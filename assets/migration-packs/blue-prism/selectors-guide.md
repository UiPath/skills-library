# Blue Prism Selectors Guide — application-model attributes and their translation

Companion to [source-guide.md § UI Target Locators](source-guide.md): how an application model records a control's recognition data per spy mode and which UiPath attribute each recorded attribute becomes. UiPath vocabulary, reliability tiers, criteria mapping, caption paths (`<nav>`), node identity and confidence tiers: the uipath-genome skill's selector translation — read it first. Observations are described by technology: SAP GUI for Windows with a French user interface spied in SAP scripting mode with Win32 windows for its dialogs and two Active Accessibility and UI Automation elements for controls the SAP mode could not see, a low-code web application in Chrome spied through the browser extension with Win32 elements for the Chrome window and its file dialogs, and UI Automation elements for Chrome's own prompts, and a Java desktop application spied through the Java Access Bridge. Work from the normalized `bp-targets.json` the source guide's `targets` command derives, never from the raw `<appdef>`. Read § Model format, § Format-wide conventions and § Pitfalls in full; the per-technology tables are a catalog — read the sections for the `technology` values the catalog contains.

## Model format

One `<element>` of an object's `<appdef>` = one control (or one window, or the application root). Its fields:

| Field | Content | Use |
|---|---|---|
| `<type>` / `<basetype>` | The spy mode and control class: `Application` (root); Win32 `Window`, `Edit`, `Button`, `Label`, `CheckBox`, `RadioButton`, `ComboBox`, `ListBox`, `ListView`, `TreeView`, `TabControl`, `StatusBar`, `ToolBar`, …; `SAPMainWindow`, `SAPUserArea`, `SAPComponent`, `SAPTextBox`, `SAPPasswordField`, `SAPButton`, `SAPRadioButton`, `SAPComboBox`, `SAPTab`, `SAPLabel`, `SAPStatusBar`, `SAPOkCodeField`, `SAPGridView`; `WebElement`, `WebTextEdit`, `WebButton`, `WebLink`, `WebText`, `WebTable`, `WebTableItem`, `WebCheckBox`, `WebRadio`, `WebList`, …; `UIAElement`, `UIAButton`, `UIAEdit`, `UIAMenuItem`, …; `AAElement`, `AAButton`, …; `HTML*` (legacy IE), `Java*`, `Terminal*`, `WindowRect` (a surface-automation region) | Decides the UiPath tag chain (§ Technology → chain) and the acting activity (the skill's rule that one tag is one node) |
| `<datatype>` | The value type the source platform reads or writes on the element (`text`, `flag`, `number`, `collection`) | A `collection` datatype (grids) → table extraction |
| `<attributes><attribute name inuse comparisontype><ProcessValue datatype value/>` | Every property the spy read; `inuse="True"` = matched at run time; `comparisontype` absent = equals, `Wildcard` = `*` / `?` patterns, `dynamic` = the value is supplied by the calling step's `elementparameter`; the source platform also offers `RegEx`, `Range`, `GreaterThan`, … (not observed) | The recorded match set — the left side of the tables below; unmatched attributes are context (`info` in the catalog) |
| Parent `<element>` nesting and `<group><name>` (groups nest at any depth) | The author's tree: application → window / page → controls, grouped by screen | The Object Repository screen the element belongs to; the path is documentation, not a selector chain |
| `<region-container name>`: the window a region spy captured, an element itself, holding `<region>`s (`<container>` = its id) | Surface-automation regions: rectangles of that window, read like elements | § Surface-automation regions |
| Element `name` | The author's caption, usually numbered and typed (`<n>.<m> [Input] <caption>`, `Button - <caption>`, `[Field] - <caption> - [Win32]`) | The element's description; the bracketed type is the author's control classification |
| `<elementparameter>` on a step's `<element>` (`name`, `expression`, `comparisontype`) | The run-time value of a `dynamic` attribute | A selector variable `{{Argument}}` bound to the workflow argument |

Prefixes group the attribute families: none = Win32 window properties (and, on an `AA*` element, its accessibility properties `Name`, `Role`, `State`, …), `w` = web (browser extension), `u` = UI Automation, `a` = Active Accessibility geometry, `p` = the parent's properties in the element's own mode (`pWindowText`, `pClassName` under a Win32 element; `pName`, `pRole`, `pID` under an `AA*` one; `pURL` under an `HTML*` one), `pa` = the parent's accessibility geometry and check state, `pu` = the parent's UIA properties. Every element also carries geometry (`X`, `Y`, `Width`, `Height`, `ScreenBounds`, `wX`, `uX`, `aX`, …) and states (`Visible`, `ScreenVisible`, `Enabled`, `Active`, `uEnabled`, `wIsEditable`, …) that are never identity.

### Format-wide conventions

- Only **matched** attributes (`inuse="True"`) were used at run time; the rest are context for the description, except the unmatched id or name of an element whose matched attributes locate it by position only (an absolute `wXPath`, a `matchindex` above 1), which identifies it (the skill's rule that position is strict and last).
- Match criteria: equals by default; `Wildcard` carries `*` / `?` verbatim into the UiPath value (the skill's rule that criteria carry over unchanged); `dynamic` becomes a selector variable bound to the workflow argument the `elementparameter` expression comes from, with the expression's fixed parts kept (`//a[text()="{{Caption}}"]` → the attribute the XPath predicate names, see § Web).
- `matchindex` (`MatchIndex`) with `matchreverse` counts among the elements matching the other attributes — position (`idx`) when above 1, flagged; a value of 1 is the default and says nothing.
- Geometry (`X`, `Y`, `Width`, `Height`, `ScreenBounds`, `w*`, `u*`, `a*` positions and sizes) and states (`Visible`, `ScreenVisible`, `Enabled`, `Active`, `Checked`, `Focused`, `Selected`, `wIsEditable`, `uEnabled`, `uOffscreen`, …) are never identity; a matched `Visible` / `Enabled` (matched on almost every Win32 element) is dropped.
- Parent attributes (`pWindowText`, `pClassName`, `puName`, `pRole`, …) describe the direct parent window or control: an ancestor tag when the leaf is not unique, otherwise description.
- The `Application` root element and the `AttachApplication` / `Launch` arguments (`ProcessName`, `WindowTitlesCollection` rows like `*<Application>*`) supply the executable and the title fragments of the scope; the source platform never records the browser executable on a web element.
- Captions are in the target application's UI language; the examples below are French (`Enregistrer sous`, `Ouvrir`, `Sélection du calcul avec tableur`); a differently localised target application changes every caption and the SAP `role` / `uia role` values.

| `wPageAddress` (`https://<host>/<app>/<page>`, `…/<app>/<detail page>?<id>…`, `https://<sso host>/<path>…`) | `<html url='https://<host>/*' />` — host kept, path wildcarded (the skill's rule that window level discriminates, it does not identify); the SSO host is a second scope | — | The WebSSO page is a third-party application: its own `<html>` scope |
| `wPlaceholder`, `wValue`, `wInnerText` (unmatched) | description | — | `wValue` / `wInnerText` of a field are its current content (the skill's rule that element purpose constrains the target tag) |

Component → activity, so substep wording and build agree: `WebTextEdit` / `INPUT` → Type Into (key events where the source pasted from the clipboard because typing was ignored — a data grid's filter fields; the sign-in password → secure text); `WebButton`, `A`, `BUTTON`, `LABEL` → Click; `WebLink` header by caption → Click with `VerifyOptions` on the class change (`*active*`, `*filter*`, `*is-active*`, `selected`); `WebCheckExists NotEqual True` after a click → `VerifyOptions` Disappears; `WebGetAttribute class / aria-expanded / disabled` waits → `VerifyOptions` TextChanges / Appears on the attribute (or a Get Attribute + compare where the source branched); `WebGetValue` / `WebGetText` → Get Text (`visibleinnertext` for a caption); `WebGetAttribute aria-rowindex / aria-colindex` → Get Attribute; `WebGetHtml` + `InStr("listbox-item")` → a Find Children / count on the list's items; `WebGetBounds` + `MouseClick` at the centre → Click on the element with the coordinate click as fallback; `WebScrollTo` → the target's scroll-into-view (implicit) or a scroll to the anchor row; `WebSetAttribute onclick=<script>` + `WebClick` + `WebGetAttribute rpa` → a row count by table extraction (no script injection); `WebSendKeys "{F5}"` → the browser refresh; `SendKeyEvents "<{CTRL}0>{CTRL}"` → Keyboard Shortcuts (zoom reset) on the browser window.

### Chrome file dialogs and prompts (Win32 / UIA)

The Open and Save As dialogs raised by upload and export are `#32770` windows of `chrome.exe`: `<wnd app='chrome.exe' cls='#32770' title='Ouvrir' />` / `title='Enregistrer sous'` (the source matched the title `dynamic` — `Ouvrir|Enregistrer sous` — from an argument), the file-name field an `Edit` inside a `ComboBox` (`<wnd cls='ComboBox' /><wnd cls='Edit' />`, `ctrlid` from a live capture), the buttons `Button` windows with caption `&Enregistrer` / `Ou&vrir` (`aaname='Enregistrer'` — strip the accelerator ampersand) or `AAButton`s by accessible `Name` (`dynamic` from the argument: `Enregistrer`, `Ouvrir`). The "allow multiple downloads" prompt and a browser-rendered sign-in popup are `UIAButton` / `UIAEdit` / `UIAElement` under the Chrome window: `<uia role='button' name='Autoriser' />`, `<uia role='edit' name='Nom d&apos;utilisateur' />`, `<uia role='custom' name='Se connecter' />`.

## HTML mode (Internet Explorer engine) → `html` + `webctrl`

HTML-mode elements (`type` `HTML`, `HTMLButton`, …; catalog `technology` `html-ie`) are read through the Internet Explorer engine, not the browser extension. An object can hold them beside browser-extension (`Web*`) elements of the same page — spied in both modes, or left from an earlier Internet Explorer version of the object — and the two are twins of one control (§ Pitfalls 6). Attributes observed: `Path`, `TagName`, `ClassName`, `ID`, `Title`, `Link`, `InputType`, `InputIdentifier2`, `Value`, `pURL`, `MatchIndex` / `MatchReverse`, geometry (`X`, `Y`, `Width`, `Height`, `ScreenBounds`), `AncestorCount`, `Enabled`, `Checked`. The names parallel the browser extension's (`wId`, `wClass`, `wValue`, `wPageAddress`, `wXPath`), and the meanings below are read from the values and those names *[Inferred]*, except where a row cites the vendor documentation.

## Surface-automation regions → image target

A region container is the window a region spy captured, the parent Win32 element its regions are anchored in (vendor documentation): type `Window`, with window attributes of its own that it is matched by, in an element, a group or another container. ## Pitfalls

1. **`inuse` is the whole truth of the match.** Every element carries thirty-odd attributes; only the `inuse="True"` ones were matched. A `wId` present but unmatched is context when the matched attributes identify the control, and its identity when they only locate it by position (§ Format-wide conventions).
2. **`dynamic` means "from the caller".** A `dynamic` attribute has no value in the model; the step's `elementparameter` expression (`Replace([xpath], "***HEADER***", [Input header])`, `"…/btnT" & [count]`, `[Pop Up Title]`) supplies it — a selector variable bound to the workflow argument, and the template's fixed parts are the recorded identity.
3. **Author-written XPaths are the attributes.** The source platform's browser extension records an absolute path by default; authors often replace them with predicate XPaths (`@id`, `@aria-label`, `@placeholder`, `text()`, `contains(@class, …)`, `@data-header`, `@wj-part`). Translate the predicates, never the path; an absolute `/HTML[1]/BODY[1]/…` path is position (low), and the unmatched `wId` or caption `wInnerText` its element usually carries identifies it instead (§ Format-wide conventions); with neither, the path itself, as one `css-selector` (§ Web).
4. **`ancestor::button[1]` names the acting node.** A caption leaf (`//div[text()="…"]`) with an `ancestor::button` axis says the click belongs to the enclosing button; start at the caption leaf and reach the `BUTTON` with `<nav up>`, or scope on the button carrying the leaf, and act on the `BUTTON` (the skill's rule that a recorded caption is the control's neighbour, not its attribute, and its rule that one tag is one node).
5. **Div-based grids are coordinate-addressed.** When the grid is not an HTML `<table>` (a `wj-*` grid), `aria-rowindex` / `aria-colindex` with `last()` arithmetic are how the source reaches cells and dimensions; there are no `tableRow` / `colName` attributes. Carry `aria-*` verbatim, find the column by its header title, state the row rule, flag the coordinates.
6. **Several objects spy the same window.** Objects each hold their own copy of the windows and shared controls they drive (each web object holds the browser window and its render surface, each SAP object its session window and dialogs); they are twins of one screen — collapse by class and title.
7. **Win32 captions carry accelerators.** `&Enregistrer`, `Ou&vrir`, `&Oui` — strip the `&` for `aaname`; the source sometimes wildcarded around it (`C*onne*xion`).
8. **`matchindex` is almost always 1.** It is recorded on most web and Win32 elements; only a value above 1 is position — a literal `idx`, flagged (`MatchIndex 4` on a SAP split button, for instance).
9. **SAP toolbar and menu functions live in code.** `pressToolbarButton`, `pressButton`, `selectedRows`, `clickCurrentCell`, `select()` on scripting ids inside code stages are UI interactions with no element in the model; `targets` lists them as `codeLocators`, and the build uses the SAP toolbar / menu / grid activities.
10. **`wnd[1]` is the same id in every dialog.** A control inside a modal dialog has the same `usr/…` id as its main-window twin; the `<wnd cls='#32770' title='…'>` scope tells them apart, and the caption is on the Win32 `Window` twin the author spied beside it.
11. **Positional radio buttons in step loops.** `usr/subSUBSCREEN_STEPLOOP:SAPLSPO5:0150/sub:SAPLSPO5:0150/…` ids address rows of a step-loop table by position; the author's element names (`[Radio Button] Table`, `[Radio Button] Microsoft Excel`) give the caption — verify live and prefer the caption.
12. **Chrome's dialogs are not Chrome's page.** The Open / Save As dialogs are `#32770` windows of the browser process, spied in Win32 and AA modes; a migration that looks for them in the page finds nothing.
13. **Page addresses reveal the environment.** `wPageAddress` holds the host the author spied on — a pre-production host as often as not — while the process opens the URL from configuration. Scope on the configured host, never on the spied one: a UI library built from web objects takes the host as an argument of every workflow that attaches to the page, per the skill's rule for a host read from configuration, with no default, since the spied host is one environment; the consuming process passes the host of its configured URL. Decide this before the consumer is authored — added afterwards, the argument touches every call site.
14. **State attributes are matched by default.** The source platform ticks `Visible`, `ScreenVisible`, `Enabled` on almost every Win32 element and the author rarely unticks them; they are state (the skill's rule that element purpose constrains the target tag) and are dropped.
15. **Localised runtime.** Captions, dialog titles, control-type names (`uLocalizedControlType`) and SAP status texts are in the robot's UI language (French in the examples here); `role` values are localized on a non-English robot. Read the target machine's language before deciding on `role` / `name` values.
