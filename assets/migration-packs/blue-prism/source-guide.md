# Blue Prism Source Guide

> **Version** followed by a number (version 6, version 7.4) is a version of the source platform.

Framework facts for extracting a genome from a **release** — the `.bprelease` package the source platform exports from a Control Room, holding processes, business objects, work queues, environment variables and their groups as one XML document — or from single `.bpprocess` / `.bpobject` exports. Follows [CONTRACT.md](../CONTRACT.md); pipeline: the uipath-planner skill's extraction; generic rules pointed to below are not restated here. Observations are described by the technology they were made on: published processes working several work queues, a SAP GUI for Windows application driven through the SAP scripting spy mode with toolbar and menu functions written in code stages, a low-code web application driven in Chrome through the browser extension with Win32 file dialogs, Outlook and Excel through extended copies of the vendor's business objects, the vendor's utility objects, custom C# and Visual Basic code objects, a Login Agent sign-in sub-process and a browser-settings sub-process. Each is an example of a shape, not a property of the framework; process, object, queue, account, host and mailbox names below are placeholders.

Release = one XML file (a few megabytes for a mid-sized package) whose `<contents>` lists every exported item; a process or object is a `<process>` tree of `<stage>` elements linked by stage ids across pages (`subsheet`s), and a business object also carries its application model (`<appdef>`: the spied elements with their matched attributes). The file is readable as text but the flow is a graph, not a list — read it through the bundled inventory script, never raw; a finding is checked against the file itself through the script's `raw` lookup, never by opening or printing the file:

```bash
# Extraction (`uipath-planner`) — read the release from a scratch folder. <WORK_DIR> lives outside the genome's folder (a temp folder, or one
# deleted after the Source Map check): a catalog beside the genome is forbidden (the skill's Source Map contract).
# `python3` on macOS / Linux, `python` on Windows.
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py check   "<EXPORT>"                     # renderer self-test, first: non-zero exit = a rendering hides a value this release carries
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py profile "<EXPORT>" --out "<WORK_DIR>"
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py cards   "<EXPORT>" --out "<WORK_DIR>"
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py dump    "<EXPORT>" <ID>                                  # every page, in execution order; a name is accepted only when it occurs once
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py dump    "<EXPORT>" "<ID or NAME>::<PAGE NAME>" --full   # one page; --full prints code bodies
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py raw     "<EXPORT>" "<NAME>[::<PAGE NAME>]" --stage "<STAGE NAME>"   # the stages' own XML (or --find TEXT, --element NAME), to check a finding against the source
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py targets "<EXPORT>" --out "<WORK_DIR>"   # application models: elements with matched attributes + the actions applied
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py data    "<EXPORT>" --out "<WORK_DIR>"   # process inventory with call edges + data sources, for the Source Map check; + page shapes, read at execution
# Build (`uipath-genome`), migration preflight — derive the catalogs into the build's working folder
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py check   "<EXPORT>"
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py targets "<EXPORT>" --out "<BUILD_DIR>/migration/source"
python3 <PACK_DIR>/blue-prism/scripts/bprelease-inventory.py data    "<EXPORT>" --out "<BUILD_DIR>/migration/source"
```

`<EXPORT>` is the `.bprelease` file, a `.bpprocess` / `.bpobject` file, or a folder holding several of them (read as one export). `profile` writes the release identity, the processes (inputs, outputs, queues, credentials, sub-process calls), the objects (run mode and shared flag, application type and launch parameters, element counts by technology, actions, code language, callers), the work queues (with spelling variants), each queue's roles (the processes that add, take, change and read its items, an action on an item given to the queue its Item ID comes from), the environment variables (secrets masked), the credential name expressions and the release's credential definitions with their access, the calendars, the groups, the stage and action vocabularies, the call graph with roots, sub-processes and what does not run (§ Call Graph Rules 11), the application models with dynamic and positional-only counts, the UI action vocabulary, the SAP scripting ids hidden in code stages, the expression vocabulary, the exposed data items, the data items read and never written (a decision on one always sees its initial value), the collection fields referenced per process (the schema of every workbook, queue item and configuration the process reads), the exception and recovery inventory, and the evidence and plumbing counts. `cards` writes one card per process and object: description, inputs, outputs, callers, pages with their narratives and interfaces, callees in order, queues, credentials, environment variables, collection fields, decisions, choices, loops, UI actions, code stages, error handling, evidence. `dump` prints one process or object page by page from each page's Start following the links: actions with their inputs and outputs, calculations, decisions with both branches, choices with every case and the named otherwise, loops with their body and their end, page and process calls with arguments, exceptions, each Recover with its scope (the whole page, or its Block and the stages that Block holds) and attempts, waits with every condition and the named timeout branch, navigate / read / write steps with the element (with its short id when its model holds the name more than once), its dynamic parameters (and how each is compared), the action, its arguments and outputs, code stages with their typed signature (`--full` adds the code, and an object's global code in a dump of the whole object or of its main page, whose ProcessInfo stage holds it), a stage type it does not read field by field with every value its XML holds, the page's data items, collections (typed fields, every initial row) and floating notes, and every stage that cannot run, in full, under `unlinked stages`: no link from the page's Start reaches it, nor from a Recover that a reached stage can enter (§ Call Graph Rules 4). The source platform has no disabled flag, so an author leaves a superseded flow unlinked; read it like a disabled block. A Start or End stage shows each parameter with its type, its data item and its description, and the page's pre- and postconditions. A data item reads `name:type="initial value"`, with `[shared]` when it is visible to the process's other pages (no `private`) and `[no reset]` when it keeps its value when its page runs again (no `alwaysinit`). Free text is on one line, a line break as ` / `; a line break inside an expression is shown as ` ⏎ ` (` / ` would read as a division). A value a text rendering (`dump`, `cards`, `profile`, the `.md` catalogs) puts in quotes is printed as written — a backslash is one backslash, a quote stays a quote — with every character a reader cannot see as `\uXXXX` (`\u000D\u000A` = a line break, `\u00A0` = a non-breaking space) and a backslash before `u` and four hex digits as `\u005C`, so every `\uXXXX` is one character (`\u005Cu00e9` = the six characters `\u00e9` as typed), and the base64 bytes a value carries by their size: an image's after its `<width>,<height>,<size>,` head, and every run of 300 base64 characters or more, on one line or wrapped at one width (a certificate), that uses 40 of the 64 characters or more and is no part of a URL or a path (the whole value, a data URI's bytes, a field of a body template); a long text, path, identifier, hexadecimal key or list prints whole; the JSON catalogs keep JSON's escapes and every value whole. No rendering cuts a value at a fixed length. `dump` takes the id `profile` and `cards` print (or the GUID): a name is accepted only when it occurs once, and a repeated name lists the copies with their ids. Read profile and cards in full; dump every process and every object with an application model the genome covers, page by page. `targets` writes the UI target catalog (`bp-targets.json` + `.md` — § UI Target Locators); `data` the process inventory (`bp-process-data.json`, a **list** with id, name, kind, groups, queues, call edges), the data sources (`bp-data-sources.json` + `.md` — § Test Data) and the page shapes (`bp-page-shapes.json` + `.md` — § Call Graph Rules 10), which execution reads and the genome does not record. Which mode reads what, and why nothing is written beside the genome: the skill's Source Map contract and its migration preflight.

`check` proves the renderings complete for the release at hand, from the release's XML itself rather than through the renderers:
- every value a stage's XML carries appears on that stage's `dump --full` line, and the line is in the dump; a Choice or Wait branch's values appear on its case line, a data item's and a collection's in its page-header entry; a stage line (a code body aside) and a case line never break;
- the process header and every page head show what the definition states, a description on one line, and the process header and its card carry every group the release lists the process in;
- each Recover names the Block its geometry puts it in and the stages that Block holds, and each page lists under `unlinked stages` exactly the stages that `check`'s own walk of the links leaves unreached;
- the cards list every page, decision, choice, loop, code stage and throw, every caller by id, and the stage logging counts;
- the `targets` entry of each element and region holds its identity and every attribute it recorded, and every UI step on it (a step on an element no model declares under `undeclared`); `bp-targets.md` shows each on the element's line;
- the process inventory holds every call's bindings and exactly the process's groups, and each process's calls are exactly its own Action and Process stages;
- the data sources, JSON and `.md`, hold every work queue with its groups, every environment variable, calendar, credential definition and Web API service;
- the page shapes hold every link of every reached stage and an `exception` link from each stage a Recover catches, and no other; each Recover's Block and the stages it catches as the geometry gives them; the shape and reasons the page's own flow classifies to; on a graph page each stage's centre; `bp-page-shapes.md` lists every page, a graph page with each of its stages and links;
- a stage whose name its page repeats carries its short id on its `dump` line and on every goto to it, and an element whose name its model repeats on every step and wait branch acting on it;
- `profile` shows the release identity, each process's row with its parameters and each object's with its callers, each work queue, environment variable, calendar, credential definition and group with its members, each call graph edge, each running object's unused and dead actions, each application model's parameters and element types, each collection's fields, the exposed data items, the exception types, and the stage vocabulary in its order; each queue's roles and the data items read and never written, from the XML's own trace of every Item ID and every write of a data item;
- every reach mark and `reach` (§ Call Graph Rules 11) is the one `check`'s own walk of the links and calls gives, and `profile` lists exactly the unused objects, the dead processes and objects with the stages calling them, and the pages of each running process that do not run;
- a data item with no initial value shows none, and no text rendering prints base64 bytes whole.

`check` also compares every element path holding a value with `<PACK_DIR>/blue-prism/schema.md`. A `schema` finding names a path no row documents (a newer version, a stage feature the pack has not met) or a flag outside its documented default, with the file and the value. No rendering shows that path, so its meaning is inferred from the path and the value or asked as a Configuration Question, and it is reported for the pack. A reading taken from a rendering that `check` fails on is not a source fact.

The source platform identifies processes, objects and stages by GUID and pages by GUID inside their process. The script derives a stable six-digit id from the GUID (CRC-32 folded into 100000–999999; the same release yields the same ids) so Source Map rows carry `` `Name` (id) `` and `check-genome.mjs` resolves the step tables' citations. Work queues keep their numeric release id. A GUID several releases hold is one definition, read from the release created last *[Inferred: the latest release carries the version in use]*: `profile` (DEFINITIONS IN SEVERAL FILES) and the `dump` header (COPIES) name the other files and whether each copy is the same; a copy that differs is another version, which `raw` prints beside the one read. Names repeat: two processes hold pages with the same names («01 - Initialize»), several objects hold an «Attach» page, and stage names repeat inside a page («Sleep», «retry + 1») — a page is named with its process, a stage with its page.

`raw` is the source itself, for checking a reading against the release rather than against a rendering (the skill's verification of suspected source defects). It prints the process or object's own attributes and its pages, then the stages named `--stage` (a data item is a stage; a stage id selects one), the stages whose XML holds `--find`, and the application-model elements, regions and region containers named `--element` (with their path through groups and region containers; children are listed by name and id and looked up on their own). `<NAME>::<PAGE>` limits the stages to one page. It reads the release afresh and prints each stage as the file holds it, every element and attribute, namespaces left out. Nothing else is dropped: an empty element is often a flag (`<private />`, `<alwaysinit />`, `<initialvalueenc />`), and a stage's geometry — `display` attributes, or `displayx`, `displayy`, `displaywidth`, `displayheight` elements on a version 6 export — decides which block, and so which recovery, encloses it. The base64 bytes a value carries are shown by their size, as in the text renderings, and secrets are masked as in every rendering. Because stage names repeat on a page, `--stage` prints every match with its stage id. `raw` is a lookup of the stages a finding cites, never a way to read a process. When the rendering and `raw` disagree, report it for the pack with the process, the page, the stage and the element.

## Detection

| Signal | Meaning |
|---|---|
| A `.bprelease` file: XML whose root is `<release>` in the `blueprism.co.uk/product/release` namespace, with `<name>`, `<created>`, `<package-id>`, `<package-name>`, `<user-created-by>` and `<contents count="…">` | Release package. Multi-component when the contents hold two or more processes, or one process plus custom business objects: **process genome** whose components are the processes and the object libraries of § Component Detection |
| `<contents>` children `process` (attributes `id`, `name`, `published`) wrapping an inner `<process name version bpversion narrative>` | Processes; `published="true"` marks the ones the Control Room may schedule |
| `<contents>` children `object` wrapping an inner `<process type="object" runmode="Exclusive|Foreground|Background">` with an `<appdef>` | Business objects; `runmode` says whether the object drives a foreground application (`Exclusive` / `Foreground`) or is code-only (`Background`) |
| `<contents>` children `work-queue` (`id`, `name`, `key-field`, `max-attempts`), `environment-variable` (`name`, `type`, `value`, `<description>`), `process-group`, `object-group`, `work-queue-group` (with `<members>`) | Platform resources and the repository folders. A release may also carry `credential` items (name, type and the processes and objects it lists, never the secret) and `calendar` items (§ Platform Resources); `schedule`, `tile`, `dashboard`, `font`, `skill`, `environment-variable-group` items are not observed — the script lists any kind by name. A `webapiservice` item is a Web API service: a business object the source platform generates from a REST definition (base URL, common headers, parameters and code, and per action the method, path, parameters, body template and output parameters); Action stages call it by its name. `profile` § WEB API SERVICES lists it and the data sources hold it whole (a secret-named literal masked) |
| `bpversion="7.1.2.3518"` on every inner `<process>` | The source platform version the definitions were saved with — the version the Source Map states. One release can hold definitions saved by several versions, and version 6 writes parts of a definition differently (§ Framework Pitfalls 19) |
| A `.bpprocess` or `.bpobject` file: root `<process>` (or `<process type="object">`) with the same inner structure and no release header | A single exported process or object: one **component** (component genome) unless a folder holds several — then the folder is the export and its identity is the file set, flagged `*[Inferred]*` |
| `<subsheet subsheetid type="Normal|CleanUp" published="True|False"><name>` under the inner process | The pages (tabs). A process's pages are its phases; an object's pages are its **actions** (its callable interface). The main page has no `subsheet` element: its stages carry no `<subsheetid>` |
| `<stage type="Data|Collection">` with `<exposure>Environment</exposure>` / `Session` / `Statistic` | Data items bound to an environment variable (read-only in the session) or a session variable (viewed and set from the Control Room) — the process's platform settings; `Statistic` stores the value in the database for reporting (not observed); with no `<exposure>` (`None`) the value is restricted to the session (vendor documentation) |
| `<stage type="Action">` with `<resource object="Blueprism.Automate.clsWorkQueuesActions" action="…"/>` | Work-queue use — the Transactional Shape (§ Component Detection and § Platform Resources) |

**Genome level** follows the contents: a root process (§ Call Graph Rules 1) over custom objects is a process genome with one component per process, a sub-process included, and the library components of the custom business objects the processes reach (§ Component Detection). One root process that starts no sub-process and reaches no library component is a component genome.

| `stage type="Start"` (`<inputs>`), `stage type="End"` (`<outputs>`), `<preconditions>` / `<postconditions>` on a Start | The page's interface — the process's arguments on the main page, an action's arguments on an object page; the pre- and postconditions are documentation the source platform never checks (vendor documentation) | Interface |

For an input an Action or `SubSheet` stage leaves blank, no vendor page says whether the callee's data item is blanked or keeps its value (the initial value, or for a shared item what an earlier action wrote), so both readings stand | Steps; call-graph edges |
| `stage type="Calculation"` (`<calculation expression stage>`), `MultipleCalculation` (`<steps><calculation>`, run in the order listed, a later one reading what an earlier one wrote *[Inferred]*) | Assignments | Data preparation; the expression carries the rule |
| `stage type="Decision"` (`<decision expression>`, `<ontrue>`, `<onfalse>`), `ChoiceStart` (`<choices><choice expression><name><ontrue>`, tried top to bottom: the first true choice is taken and the rest are not evaluated) + `ChoiceEnd` (the otherwise, same `<groupid>`) | Branches | Business Rules |
| `stage type="LoopStart"` (`<looptype>ForEach`, `<loopdata>`) + `LoopEnd` (same `<groupid>`) | Iteration over a collection | Steps ("for each …") |
| `stage type="SubSheet"` (`<processid>` = a page id of the same process, `<inputs>`, `<outputs>`), `stage type="Process"` (`<processid>` = another process's GUID) | Page call; sub-process call | Call graph |
| `stage type="Exception"` (`<exception type detail localized usecurrent savescreencapture>`), `Recover`, `Resume`, `Block` (geometry only) | Error handling | Error Handling; `usecurrent="yes"` is a rethrow; a Recover inside a Block handles that block, elsewhere the whole page |
| `stage type="Navigate"` / `Read` / `Write` / `WaitStart` (+ `WaitEnd`) with `<step><element id><elementparameter>…</element><action><id><arguments>` or `<choices><choice reply><element><condition><id><arguments><comparetype>` | UI actions on application-model elements (objects only) | Steps and the target catalog (§ UI Target Locators) |
| `stage type="Code"` (`<inputs>`, `<outputs>`, `<code>`) | Inline code in the object's language | The activities that do its work (the skill's rule that wrappers are not components), a coded step, or a UI interaction hidden in code (§ Framework Pitfalls) |
| `stage type="Note"` (`<narrative>`) — linked into the flow or floating | Author comments | Wording; never a step |
| `stage type="Anchor"` | Routing only | Skipped by `dump` |
| `stage type="Alert"`, `Skill` (not observed) | Alerts to the Control Room; Digital Exchange skills | Deployment note; nearest skill |
| Per stage: `<display x y w h>` (version 6: `<displayx>`, `<displayy>`, `<displaywidth>`, `<displayheight>`), `<font>`, `<loginhibit onsuccess>`, `<breakpoint>`, `<narrative>` | Layout, logging switch, debugging | Fonts and breakpoints are never read; positions decide the Block that encloses a stage (§ Framework Pitfalls 2) and place the shape catalog's stages (§ Call Graph Rules 10); `loginhibit` feeds § Evidence; a stage `narrative` is the author's note — except the vendor's description of an internal action, copied into every call (§ Framework Pitfalls 5) |
| Object `<appdef>`: `<apptypeinfo><id><parameters>`, `<element>` tree with `<group>`s nested at any depth, and `<region-container>`s of surface-automation `<region>`s | Application model | Target Applications, target catalog |
| `<view>`, `<camerax>`, `<zoom>` | Designer camera | Never |

Excluded from logic: the `Initialise` main page and the `Clean Up` page of an object when they are empty, as in the vendor's objects (a non-empty one runs for every instance of the object — § Call Graph Rules 5); `Anchor` stages; floating notes (wording only); `Block` stages (geometry, read only to scope a Recover); stages no link from a page's Start reaches, nor from a Recover a reached stage can enter (`dump` lists them as unlinked), and the pages, processes and objects only such stages reach — dead code for the Source Map (§ Call Graph Rules 11); the standard and utility business objects' internals (their actions map to UiPath activities — § Component Detection); the stock narratives of internal actions; Login Agent pages (§ Component Detection); `Sleep` actions (timing → Error Handling wording, never a step); a force-close of an application before its launch (cleanup wording); a process's own log-file writes and screenshots (evidence policy, § Evidence); data items nothing reads (dead constants, debug flags) — a collection an internal Collections action names in its `Collection Name` text is read, though no `[name]` shows it.

## Component Detection

The source platform has two artifact kinds — processes and business objects — and the release carries both plus the source platform's resources. Components come from the **processes and the objects' application models**, not from files:

| Construct | Component type | Skill | Rationale |
|---|---|---|---|
| A **root**: a process no `Process` stage of another process calls (§ Call Graph Rules 1), with its pages | One **RPA process**; its work-queue actions fill the Transactional Shape's As-is table — it consumes items where it takes them (`Get Next Item`, `Mark Completed`, `Mark Exception`) and produces them where it adds them (`Add To Queue`); how the roles are split at build is an execution decision, not a property of the process | `uipath-rpa` (Process project) | A published root is what the Control Room may schedule (§ Detection); an unpublished one the Control Room cannot start as exported, so how it is started is a Configuration Question. Its pages are its phases. Two roots in a release are two processes |
| A **sub-process** (`Process` stage target) | Its own component: an **RPA process**, published or not. One the release does not publish gets no trigger: the Control Room cannot start it, so it runs only when another process invokes it. One that only signs the robot in or sets the screen is robot plumbing (Login Agent row) | `uipath-rpa` (Process project) | One component per source process keeps its name, so a later release that starts the same sub-process finds it; a copy per caller drifts |
| A **business object with an application model** (`<appdef>` with elements, `runmode` Exclusive or Foreground) | One **UI library** per object (its applications in the Object Repository, one screen per window or page) | `uipath-rpa` (Library project, one public workflow per called action) | An object is the application's reusable interface; its published pages (actions) are the library's workflows and their Start inputs / End outputs the arguments. One library per object keeps the object's and its actions' names, so a later release that calls the same object finds them. Two objects for one application, a copy used beside its original, are two libraries; twins collapse only within one library |
| A small object that drives the **browser's or OS's dialogs** for another application (Open / Save As, download prompts, the browser launch) | Its own UI library, as any business object | `uipath-rpa` (Library project) | One library per object, as above; in the Object Repository its dialogs are screens of the browser application |
| The vendor's **standard business objects**, known by exact name — the VBOs the source platform installs with the product or publishes as its own on the Digital Exchange (vendor documentation): `MS Excel VBO`, `MS Word VBO`, `MS Outlook Email VBO`, `MS Outlook VBO`, `MS Outlook VBO (NetOffice)`, `Google Sheets VBO`, `Blue Prism MAPIEx`, `Email - POP3/SMTP/IMAP`, `Email - POP3 IMAP SMTP`, `Data - SQL Server`, `Data - OLEDB`, `System - Active Directory`, `Webservices - REST`, `Webservices - OAuth2.0`, `Utility - Collection Manipulation`, `Utility - Date and Time Manipulation`, `Utility - Encryption`, `Utility - Environment`, `Utility - File Management`, `Utility - Foreground Locker`, `Utility - General`, `Utility - HTTP`, `Utility - Image Manipulation`, `Utility - Image Search`, `Utility - JSON`, `Utility - Locking`, `Utility - Maths`, `Utility - Network`, `Utility - Numeric Operations`, `Utility - Strings`, `Utility - Windows Compressed File`, `Utility - XML`; and `Regular Expression Information Extractor`, which no vendor page names — code-only objects, usually in the `Default` group, whose pages are in the release when it was packaged with them | Not components: each called action is a UiPath activity (Excel, Mail, DataTable, File, String, Date, Process) with the behaviour its page has (§ Internal and stock actions); an object under one of these names that adds or changes a page is a fork (next row) | `uipath-rpa` (activities of the calling project) | Library code that UiPath's packages provide; the genome states the behaviour (read the sheet, send the mail), never the object |
| A **fork of a standard object**: a copy the customer extended, named after it with a prefix or suffix or kept under the vendor's own name, carrying the vendor's pages beside added or changed ones | Its pages that match the vendor's page are the standard behaviour (row above); a page it added or changed is read as a custom code object's action (next row) | `uipath-rpa` | The source platform extends an object only by copying it, and nothing in the export marks which page changed: tell them by reading the page (signature, stages, code) against the vendor's, never by the name |
| A **custom code object** (C# or Visual Basic code stages behind its actions) | Each called action is read for what its code does. One whose code does what one or a few UiPath activities do — open a workbook read-only, filter a column and read the visible rows, sort a range by the columns its caller passes, convert a date to text in a format, read a workbook through OLEDB, copy a folder, take a screenshot — is a wrapper: steps of its caller (the skill's rule that wrappers are not components), and so is an action whose result only builds a wrapper's inputs (a column number turned into letters for the range text a sort takes). The rest, logic of its own around the activities as that rule names it — here date arithmetic with public holidays, key/value transposition, a custom property of a workbook or a mail item such as an add-in's classification, switching the mail client offline — is the object's **library**, one public workflow per called action; an object with none left is no component, an action that only writes the run's own log file is the evidence policy (§ Evidence), and one that reads the process's configuration file or turns its key / value rows into the settings row is the process's configuration (§ Platform Resources), whatever else its object does | `uipath-rpa` (activities of the calling project; Library project for the rest) | The logic is in the release (the `<code>` text); the genome states the contract and the rule (e.g. which public holidays), and the build writes in C# only what no activity performs. One library per object, as for UI objects |
| **Login Agent** (the vendor's `Login Agent` object, the login sub-process, screen-resolution objects, the `Login Format String` environment variable, the `Windows Login: <machine>` credential) | Not a component: robot session plumbing | — | The source platform signs the robot into Windows and sets the resolution; UiPath's unattended robot does this as machine settings. ### Layout and names

Owners find a process or an object by its group. Processes, objects and work queues each have their own tree of groups, which nest; a release lists every group with members, its `name` the full path with `/` between levels, so a parent group with no members of its own appears only inside its children's paths. The default group is the one flagged `isDefaultGroup`, whatever it is called, since it can be renamed (vendor documentation). A group lists its members by id; each process's and object's memberships are its `groups` (`{path, default}`) in the process inventory and on its `dump` and `cards` headers, and a work queue's in the data sources; a single `.bpprocess` or `.bpobject` file carries no groups. | Source platform | UiPath |

| A page of that process | Workflow at the project's root, named after the page as written; the Main Page is the entry workflow |
| An action of that object | Workflow at the library's root, named after the action as written; in a project the library is folded into, at `<group path>/<object>/<action>` |

### Internal and stock actions

An action's body decides the step, never its name: `Run Process Until Ended` waits for the process to end, `Wait for Process` for one to start. An internal object's action is described by the vendor's text every call carries (`vendor text`). The vendor revises a standard object's pages between versions, so the page a release holds is the authority; the rows give the vendor's pages as shipped (`vendor page`), the only reading of a standard object a release calls but does not hold, flagged `*[Inferred: the vendor's page as shipped]*`. An action no row covers is read on its page (`dump "<object id>::<action>" --full`).

| Action | Behaviour | Known from |
|---|---|---|
| Work Queues `Get Next Item` (Queue Name, Key Filter, Tag Filter, Sort Order → Item ID, Data, Status, Attempts) | Locks and returns the next item: lowest priority number first, then the longest waiting, never one locked, completed or deferred to a later time. A Sort Order (from version 7.4; blank is Priority) of Priority and SLA breaks a priority tie by the shortest remaining SLA, and SLA ignores priority (vendor documentation). An empty Item ID means none is available — the queue is empty or stopped, which is how a Control Room stop ends the consumer loop after the current item | vendor text |

### Value syntax

`[Name]` a data item; `[Collection.Field]` the field of the collection's current row: inside a loop the row the loop is on, outside one the first row until a loop over the collection ends, then no row until a loop or `Add Row` sets one — reading a field with no current row raises an error — and a single-row collection's one row always (vendor documentation); literals, operators and functions: § Expression Translation. An `input`'s `expr` on an Action is the argument; an `output`'s `stage` the data item that receives the result. A `password`-typed data item is a secret: its initial value is stored encrypted (`initialvalueenc`, empty when the item has none — `dump` then shows no value), as is a password cell of a collection's initial row (`encvalue`, shown as `***`) and the script never prints it; a literal typed into a password field or assigned into a password-named text item is masked wherever it appears (a flag or number named like one, such as `Password Expired`, holds a state and stays visible) (`Write` of `[Password]`, `Start Process` arguments carrying `-pw=`). Credential **names** (`"<prefix>_SAP_"&[machineName]`) are identity and stay. A literal initial value is a Configuration Question default when its value is open, otherwise a fact stated where it acts (the skill's Configuration Questions rules).

**Data types are typed, and one of them is a trap.** A data item, a collection field, an action input and an environment variable each carry one of the source platform's types; the genome states the type in behavioural words (a number, a date, a flag, a password) and execution maps it. The mapping that matters:

| Source type | UiPath type | Note |
|---|---|---|
| Text | `String` | comparison and case: § Expression Translation |
| Number | `Decimal` (or `Double`) | a source platform number is a decimal of arbitrary size — an account number, a document number or an amount typed as `Int32` overflows at ten digits; `Int32` only where the source uses the item as a counter or an index |
| Flag | `Boolean` | |
| Date, DateTime, Time, TimeSpan | `DateTime`, `TimeSpan` | The source platform holds a datetime as UTC (the vendor's time-zone code says so) and `Now()` returns UTC, `LocalTime()` the local time; keep which one the source used |
| Password | `SecureString` | never text (§ Framework Pitfalls 11) |
| Collection | `DataTable` with typed columns | a single-row collection is the author's record type: its fields become typed values (variables, arguments), or a dictionary where they are read by name (settings, queue item data), and only a collection of rows is a `DataTable`; `[Collection.Field]` is the current row |
| Image, Binary | an image, a byte array | a picture (a screen capture) and binary content such as a file's (not observed) |

## Target Resolution

1. **`apptypeinfo` → application.** `Win32Launch` / `Win32Attach` with `Path` = the executable (`saplogon.exe` → SAP GUI for Windows; `chrome.exe` → Chrome for its native dialogs); `BrowserLaunch` / `BrowserAttach` with `Path` = the browser executable and optional flags (`-incognito`) → `<html app>` per the skill's `html` tag; `WindowTitle` = the accepted window title (usually `*`); `ProcessName` / `ProcessID` on `AttachApplication` steps (`"saplogon"`, `"chrome"`, `[Process Name]`) → the executable when the model has no path. A `Background` object with a one-element model (the `Application` root only) drives nothing.
2. **Web page host.** The `wPageAddress` information attribute of web elements holds the URL the element was spied on (`https://<host>/<app>/<page>`) → the `<html url='https://<host>/*'>` scope, and a Configuration Question for the environment URL when the process opens the URL from a data item, an environment variable or a configuration key — the spied host is then one environment, not the one to scope on ([selectors-guide.md](selectors-guide.md) § Pitfalls).
3. **Windows.** `Window` elements' `WindowText` / `ClassName` (`SAP_FRONTEND_SESSION` = a SAP GUI session window, `#32770` = a dialog, `Chrome_WidgetWin_1` = the Chrome window, `Chrome_RenderWidgetHostHWND` = the Chrome render surface, `SAP Logon *` = the logon pad) name the application's windows; the SAP object's `Window` elements with `SAP_FRONTEND_SESSION` and a French caption are SAP screens seen through the Win32 spy — the same application as the `SAP*` elements.
4. **SAP systems.** A SAP sign-in through the shortcut launcher (`Start Process` of `sapshcut.exe -system=… -client=… -user=… -pw=…`) or through the SAP Logon pad names the system and client: one Target Applications row per SAP system the process signs in to, reached through one SAP GUI installation; where the system and client codes come from (a literal, configuration, a mapping table, a choice stage in the sign-in action) is a Configuration Question. The SAP Logon activity opens a session by the connection name SAP Logon lists, which the codes do not give, so that name is a Configuration Question for each system. A `-pw=` argument is fed from a `Credentials.Get` output — a credential asset, never a value.
5. **Excel and Outlook** through the vendor's VBOs are desktop applications the process uses (workbooks read and written, mails sent and read) — Target Applications rows without UI targets.
6. **Shared folders** (UNC roots in environment variables, configuration keys for a drop folder and a report folder) → Platform Dependencies (storage bucket or the kept share); the local processes root → a Text asset.
7. **Mailboxes**: environment variables holding functional mailbox addresses are Text assets; a literal personal address in a Send Email input is personal data — the genome names the role (the support mailbox) and the Source Map notes the deviation.
8. **Login Agent** (`Login Agent` object, `Get Credential Name`, `Log In`, `Unlock Screen`, the domain literal) is the robot's Windows session, never an application.

## Call Graph Rules

1. **Roots** = processes no `Process` stage of another process references, published or not: an export can carry its main process unpublished. **Sub-processes** = processes a `Process` stage of another process references. **Objects** = leaves reached through `Action` stages; an object's own `Action` stages on other objects are edges between their libraries, or to the standard objects. An export holding objects and no process is one library per object: every published action is an entry point, because its callers are outside the export and nothing in it can show an action unused (`profile` says so beside ROOTS).
2. **Order inside a page**: from the page's `Start` stage follow `<onsuccess>`; a `Decision` forks into `<ontrue>` / `<onfalse>`; a `ChoiceStart` into its choices' `<ontrue>` and the `ChoiceEnd`'s `<onsuccess>` (otherwise); a `LoopStart`'s `<onsuccess>` is the body until the `LoopEnd` with the same `<groupid>`, whose `<onsuccess>` continues after the loop; a `WaitStart` forks into its choices and the `WaitEnd` (timeout); `Anchor`s are passed through; `End` and `Exception` end a path; a link to a stage already printed, a loop or a merge, is `→ goto ‹name› [type]`, followed by the stage's short id (`#` and the first eight characters of its stage id) when its page holds the name more than once, as is that stage's own line. Stage document order is **not** execution order.
3. **Pages** run in the order the main page reaches them; the tab order (`<subsheet>` list) is the author's grouping and usually agrees. A page called from several callers is one step; the callers' steps reference it.
4. **Recovery**: a `Recover` stage is entered when an exception is raised inside its scope — the innermost `Block` it sits in (a stage whose centre lies inside the block's rectangle on the same page — § Framework Pitfalls 2) or, outside any block, the whole page; unhandled exceptions propagate to the calling stage of the parent page, up to the main page's recover. From the Recover until a `Resume`, the page is in recovery mode: a further exception is not caught by the same Recover and goes to the next level — the page's Recover for a Block's, the caller for the page's (vendor documentation). The path from a `Recover` (through `Resume`) rejoins the success flow or rethrows. A Recover with an attempt limit (`attempts=` on its line, at most 100) recovers at most that many times; at the limit the session terminates, or, with its Raise exception to parent page option (`bubbleException`), an exception is raised on the parent page (vendor documentation). Whether the count restarts each time the page runs, and whether the parent page's own Recover catches that exception, is undocumented. A Recover whose scope holds no stage that can run is never entered — `dump` lists it and its path as unlinked.
5. **Object actions** = the object's `Normal` pages. The source platform runs the `Initialise` main page itself when it creates the object, before its first action, and the `Clean Up` page when the calling process ends, even after a failure; neither can be called. The global code and every code stage compile into one class whose member variables the whole object shares, and the object lives from its creation to the end of the process, so its shared data items, whichever page declares them, and the global code's fields keep their values from one action to the next — the attached application, a handle; `alwaysinit` resets an item whenever the page holding it runs (vendor documentation). The process and each object that calls the object hold their own instance of it, each with its own attached application, unless the definition is shareable (`shared="True"` *[Inferred]*, on its `profile` row, its card and its `dump` header) or shares the model of one: then every caller of the run reaches one instance, and only a sub-process gets another (vendor documentation). An action's interface is its `Start` inputs and `End` outputs, which the caller's `Action` stage binds, plus the **object state** it reads or writes: a shared item or global-code field one action sets — through a Calculation, an output, a `Start` input stored in it, a code stage or the Initialise page — and another reads, or the same action reads on a later call before setting it; and, for an object it calls that has state, its own instance of that object. Object state and a non-empty Initialise or Clean Up page are part of the library — values carried between calls, set-up every action relies on, a close-down at the end of the run — built per the skill's rule on state kept between calls, with the instances above deciding who holds it. The attached application crosses calls as that rule states, and an `Attach` reads as § Step vocabulary → behaviour, the `Attach` / `Detach` row, states. A shared item no page sets is a constant (§ Signals — Process (and object) pages), and one an action always sets before reading it belongs to that action. Actions and objects nothing that runs reaches are unused parts, extracted or named in the Source Map as the skill's Unused parts question decides, unless only dead code reaches them (rule 11). Pages an action calls inside the object (an `Attach` page every action starts with, a `Write Via Bounds` helper) are folded into the action's step, and `profile` does not count them unused.
6. **Duplicated pages.** Pages that differ only in name and a literal (an export page per document type, a sign-in page per system) are one workflow with the literal as an argument; a duplicate no caller reaches is excluded and named in the Source Map.
7. **Counting for the skill's complexity inference**: "workflow files or nodes carrying logic" are the pages reached from the main page (a process) or the actions the library carries; "entry points" are one for a process, its main page, or one for a library; "conditional branches" count `Decision` and `ChoiceStart` stages; "error-handling constructs" count `Recover` stages and the `Exception` stages that raise (not `usecurrent`) — a blank type is common and still raises.
8. **Identity** in a step table's Source objects cell: `` `<process or object name>` (id) `` with the six-digit id from `profile` / `cards` / `data`; the page as its locator, `` `<name>` (id, page `<page>`) ``, so a page is always qualified by its process (page names repeat across processes); stages by name, `` (id, page `<page>`, stages `<stage>`, `<stage>`) ``, only when a page yields several steps.
9. A `Process` stage into a process absent from the release is an unresolved call (Source Map); an `Action` on an object absent from the release is unresolved too — `profile` lists both.
10. **Shape.** `data` writes each page's shape (`bp-page-shapes.json` + `.md`): `blocks` when the page reads with sequences, branches that meet, ordered choices, loops left at one place (breaks and continues of the innermost loop allowed) and a try / catch around a run of stages whose catch rejoins at the run's next stage or ends; otherwise `graph`, with its reasons — `loop-multi-exit` (a loop left towards two places, a break out of two loops at once included), `jump-into-loop` (a loop entered at two places), `shared-tail` (a stage reached by branches that do not otherwise meet), `shared-handler` (one Recover catching several runs). Per page: `nodes` (stage id and short id, name, type, `kind`, Block, `region` and `run`, centre `x, y`), `edges` (`from`, `to`, `kind`), `regions` (the Recover, its Block, the stages it catches, its `runs` with their entry and exits, its handler stages and Resumes with their continuations), `unlinked`. The nodes are the page's reached stages and its notes, the edges its links: Anchors, linked Notes and a Choice's or Wait's end are passed through, the End stages meet at one end, a throw or rethrow ends its branch with nothing to meet, and a Loop carries its implicit links (an empty collection straight past the loop, the end back to the start). A Recover's scope (rule 4) splits into runs a try / catch can hold whole, each entered only at its first stage and left towards one stage, each run's failure leading to the Recover; a catch rejoins only at its run's next stage, or breaks or continues the loop around it. A Block inside another Block's scope splits the outer scope's runs, since the inner handler raises to the caller (rule 4). A break's branch holds the stages only the loop reaches after it, up to where the breaks meet; a link to the loop's condition or to a Loop's end is a continue. A loop over a collection continues after every break where its done link leads, so its breaks meet there. Each node carries its stage's centre (pitfall 19), each region its Block's corner and extent. Every page with a Start is listed, called or not. Most pages read as blocks: merges, a retry loop left at one place, a recovery that resumes at the Block's next stage or ends.
11. **Reach.** What runs starts at the roots' main pages (`profile` ROOTS, each with its published flag) or, in an export of objects only, at every published action (rule 1), and follows the stages each page's links reach (rules 2 and 4): a reached Page stage runs its page, a Process stage the callee's main page, an Action stage the action's page of the object it names and that object's Initialise and Clean Up pages (rule 5). An unlinked stage is dead code. A page, process or object that does not run is an unused part (rule 5) when no stage but its own calls it, or such a part runs it; any other is dead code, which only unlinked stages and other dead code lead to, a page calling itself behind an unlinked stage included. `profile` § CALL GRAPH marks each call by its stage, `[unused]` or `[dead]`, and lists the unused objects, the dead processes and objects with the stages calling them, the pages of each running process that do not run and each running object's unused and dead actions; the object callers, queue roles, queue tags and credential and calendar reads in `profile`, the page heads in `dump`, and the pages, callers and callees on the cards carry the same marks, and the process inventory's items, pages and calls a `reach` (`runs`, `unused`, `dead`). A published process only dead code calls may still be started on a schedule of its own (§ Platform Resources): whether one starts it is a Configuration Question.

## Expression Translation

Expressions sit on Calculation, Multiple Calculation, Decision and Choice stages, in call inputs, and in a Wait's timeout and replies. `[Item]` reads a data item, `[Collection.Field]` a field of the collection's current row. Literals: text in double quotes with `""` for a quote, numbers with `.` for decimals, `True` / `False`, dates as text in `dd/mm/yyyy`. `&` joins text, `+ - * /` compute, `= <> < > <= >=` compare, `AND` / `OR` / `NOT` combine (in any case: `or` too), parentheses group. The source platform casts between its types silently where an expression expects another — `Len(100)` is 3, the number read as the text "100" — so a comparison or a join mixing text and numbers is ordinary here; state each value's type in the rule.

**Case.** The documentation states no case rule for comparing text. Read `=`, `<>`, `InStr`, `StartsWith` and a Wait's `Equal` / `Wildcard` comparison as case-sensitive *[Inferred: authors wrap both sides in `Upper` / `Lower` where case must not matter]*, and write "case-insensitive" only where the source upper- or lower-cases both sides. Queue names are case-insensitive (§ Framework Pitfalls 8).

Collection filter strings (`[Key] LIKE '<Prefix>_%'`, `[Created] < '<date>'`) read as "rows whose key starts with …", "created before …".

Whether a retry attempt keeps the tags of the attempt before it is undocumented; the vendor documentation says only that the item is requeued with an incremented attempt number.

1. **Set when added, never changed** → its data. When every fetch filters only on such a tag naming item kind or source (`SOURCE:<application>`), of which each item carries exactly one value → one queue per value, each item in one queue. Any other filter is case 4; an item is never copied into several queues.
2. **Parent key** (children of one parent) → children of different parents interleave (the skill's rule that several levels of items are one unit of work). 3. **Changed only on the held item, read by nothing afterwards** → the progress text while the item is worked, its output data when it completes.

The record store keys its records by the item's reference, which the queue then enforces as unique: a key field that repeats across items is extended until it does not. A tag a later attempt reads is a Configuration Question with both readings of the retry: kept, then the record, which outlives the attempt, carries it; dropped, then the retry clears the record's tags and the phase state is re-derived from evidence (the queue item lifecycle row).

## UI Target Locators

Every business object carries its **application model** (`<appdef>`): one `<apptypeinfo>` (how the application is launched or attached) and a tree of `<element>`s — nested in one another and in `<group>`s at any depth, and surface-automation regions in a `<region-container>`, the window the region spy captured ([selectors-guide.md](selectors-guide.md) § Surface-automation regions) — each with a `<type>` (the spy mode and control class), `<basetype>`, `<datatype>`, and `<attributes>` — every property the spy read at design time, of which only those with `inuse="True"` are matched at run time (with a `comparisontype`: equals when absent, `Wildcard`, `dynamic` = supplied at run time by the step's `elementparameter`). Stages reference elements by id from `Navigate` / `Read` / `Write` steps and `WaitStart` choices, so the actions applied to each element are known. `targets` writes one normalized record per element (`bp-targets.json`): `object`, `application` (type, parameters), `elements[]` with `id`, `name`, `path` (the ancestor element names), `group`, `type`, `technology` (`sapgui`, `web`, `win32`, `uia`, `aa`, `java`, `terminal`, `region`, `other`), `matched[]` (`name`, `comparison`, `value`), `info[]` (`name`, `value`, and `comparison` when set: every attribute the spy recorded with a value and does not match on - the candidates a rebuilt selector may use), `description`, `narrative` (the markup the spy recorded), `dynamic`, `positionalOnly`, `actions[]` (stage, page, kind, action id, arguments, element parameters, written value, read target, wait comparison and expected value) — `undeclared[]`, the ids that UI steps name and no model of the object declares (a page copied from another object, an element deleted since), with their actions: no identity to migrate, so the element is captured live — and `codeLocators[]`, the SAP scripting ids found in code stages (§ Framework Pitfalls). `bp-targets.md` lists the same per object, each element by path, name and id (ids repeat across objects — § Framework Pitfalls 21), a long image value by its size. Formats and per-attribute translation: [selectors-guide.md](selectors-guide.md). Extraction records only counts (elements per technology, dynamic, positional-only, never acted on, scripting ids in code) in the Source Map; execution derives the catalog at migration preflight and turns it into Object Repository targets (the skill's migration at execution).

Several elements usually describe the **same control**: the objects that drive one application each spy their own copy of the window and of shared controls (each object driving a browser application holds the browser window and its render surface; each SAP object its session window), and a "dynamic" element (an XPath template, a SAP id ending in a counter) stands for a whole family of controls. Collapse at execution by window + matched attributes (the skill's Object Repository identity rules); a dynamic element becomes one parametrised Object Repository element with a selector variable. Elements never acted on (spied for a check that was later removed, or kept for other processes) are counted and excluded.

UI interaction sits in the application objects (Navigate, Read, Write and Wait are object stages): size UI work per object from its elements per technology.

## Test Data

A release carries **no data rows**: the work is in the work queues (not exported), the settings in configuration workbooks on a share (not exported), the credentials in the Control Room. What drives a run, and what `data` writes as the recordset list (`bp-data-sources.json`, `[{id, name, kind, drives, usedBy, …}]`):

| Where | What | `data` kind (`drives`) |
|---|---|---|
| `work-queue` items and every queue name a process resolves from its data items (`[workQueue1]` → the literal initial value) | The queues — the data sets that drive the steps; `keyField`, `maxAttempts`, whether the release defines it, its spellings (queue names are case-insensitive), the actions per caller | `work-queue` (true) |
| `environment-variable` items and exposed data items | Deployment settings (value masked when the name says secret) | `environment-variable`, `session-variable` (false) |
| `Credentials.Get` name expressions, the release's `credential` definitions | The accounts (§ Platform Resources) — names, types and access, never secrets | `credential` (false) |
| `calendar` items, the `Calendar Name` a Calendars action reads | The working-day calendars (§ Platform Resources) | `calendar` (false) |
| Collection fields referenced in expressions or declared in `collectioninfo`, per process (`<process>::<collection>`) | The **schemas**: queue item data (the fields of the collection passed to `Add To Queue` and read from `Get Next Item`), configuration keys (`config`), workbook columns, grid columns | `collection` (false) |
| File, folder, workbook, sheet and URL expressions passed to actions (input names containing file / path / folder / directory / workbook / worksheet / url / link / command) | The paths and names the process builds — the paths Configuration Question material, the names stated in the steps that use them | `path` (false) |
| Send Email recipients and subjects | Mail contracts | `mail` (false) |
| `Start Process` / `Kill Process` / `Run Process Until Ended` / `Launch` arguments | External processes and scripts (kill-before-launch, a batch relaunching Outlook, xcopy of a browser profile, PowerShell one-liners) | `external-process` (false) |
| Environment lock names; `Launch` / `AttachApplication` / `WebNavigateApplication` steps | The lock; the application launches | `environment-lock`, `application-launch` (false) |

`bp-process-data.json` is the process inventory `check-genome.mjs` reads: `[{id, guid, name, kind (process | object), published, runmode, groups [{path, default}], reach (`runs` | `unused` | `dead`, § Call Graph Rules 11), recordset (the first queue the process takes items from, else null), queues {name: {action: count}} (the item-keyed actions — `Update Status`, `Mark Completed`, `Mark Exception`, `Defer`, `Tag Item` / `Untag Item`, `Set Data`, `Get Item Data` — carry no queue name; `profile` § QUEUE ROLES states the queue each is attributed to), pages [{name, type, inputs, outputs, reach}], inputs, outputs, credentials, environmentVariables, screenshots, notes, calls [{stage, page, kind (process | object), callee, action, calleeId, internal, recordset: null, reach, inputs, outputs}]}]`. Rules: a queue named under two spellings is one queue (`spellings`); a `password` data item's initial value and any literal assigned into it are masked; the collection initial rows the author typed (button numbers per case, sort columns, accepted window titles) are lookup rules for Business Rules, not test data; a data item's literal initial value is a source value only when the process reads it (a queue name, a process name, a sheet name, a limit), not when a later calculation overwrites it.

## Provenance the Source Map must carry, and the inventory shape

Export identity: the release file path, the release name, creation date, package id and name (the creator's address is not carried), the source platform version (`bpversion`), the contents count by kind (`profile` § EXPORT). Source object identity: `` `<process or object name>` (id) `` with the id from `profile` / `cards` / `data` (CRC-32 of the GUID), a page as its locator (Call Graph Rules 8), work queues as `` `<queue name>` (id) `` with the numeric release id. Per workflow step, its step table row: Source objects the processes or objects and the pages the step was built from; Data sets the work queues those pages take items from; the queues it adds to and the objects it invokes that are steps of their own in Notes. Checkpoints: none — a process is not a test suite; its `WaitStart` verifications are the acting steps' post-conditions (the skill's rule that verification is a property of the acting activity), and a process built as a test would list its Decision-based comparisons. Inventory counts: processes (published roots, sub-processes), objects (with and without application models), elements per technology, dynamic and positional-only elements, elements never acted on, SAP scripting ids in code stages, work queues (and spelling variants), environment variables, credential name patterns, configuration keys, stages per process, unused actions per object.

## Evidence

A stage's logging is one of three options: no `loginhibit` element = every run logged, `<loginhibit onsuccess="true"/>` = logged only when it fails, a bare `<loginhibit/>` = never logged *[Inferred from the three stage logging options; the XML does not name them]*. Production processes log almost no stage on success, so the session log is the exception log and says nothing about what the author considered a milestone. What the source records on purpose is elsewhere: a **log file of its own** (`Append to Text File` with a dated name, one line per event), **screenshots** (a screenshot object, `Exception savescreencapture="yes"`), **queue item statuses and tags**, **mails** with attachments; `Note` stages are the author's comments (wording), `Alert` stages (not observed) are Control Room alerts (Deployment). The skill's evidence policy states, once per component, what the source records and where — the rebuilt process logs the milestones the source's stage names describe (sign-in per application, item taken, phase completed, outcome) and the same own-log lines, the log file itself only where the skill's evidence policy keeps it, attaches the same screenshots — and gives it an acceptance criterion. Stage logging is the engine's own record of each stage it runs (the skill's table of source steps that are not UI actions): no log message, and never one activity per logged or inhibited stage. `profile` § EVIDENCE AND PLUMBING and `cards` report notes, sleeps, screenshots and the stage logging per process (`logging: all / errors-only / none`).

A common production shape: logging inhibited on nearly every stage, a `;`-separated **security log** of the process's own (timestamp, process, application, action) appended to a dated file at every application sign-in, sign-out and workstation clean-up, and a screenshot taken only for the technical-error mail.

**Checkpoints for the Source Map.** A process release asserts nothing formally; `WaitStart` conditions after actions are verifications of those actions and Decisions on read values are business rules. A process used as a test (one that only reads and compares) would list its Decision comparisons as checkpoints — `stage — asserts — expected — screenshot?`; none in the observed release.

## Framework Pitfalls

Source platform facts — true of every release:

1. **Stages are unordered in the file.** Document order is creation order; only the `onsuccess` / `ontrue` / `onfalse` / choice links say what runs next, and one page can hold several disconnected flows (the success path and the recovery paths). Read `dump`, never the XML.
2. **Recovery scope is geometry.** A `Recover` inside a `Block` rectangle handles the stages inside that rectangle; a `Recover` outside any block handles the whole page — including its sub-page calls. Blocks look like decoration and decide which retry applies where (`dump` prints the scope). A Block's `display` x, y is its top-left corner and w, h its extent, while any other stage's x, y is its centre: read as a centre, the rectangle moves by half its size and most Recovers fall outside their Block.
3. **Recovery paths look like steps.** The `Recover` → read exception → Decision on type → `Resume` → retry counter → back to the phase start idiom is Error Handling ("business → return; otherwise sign in again and retry up to N"), not a workflow step; a `Resume` that rejoins the success path with a flag (`IsBusiness? = True`) is how a page returns a business outcome to its caller. The page shapes keep the idiom's stages as nodes of the page's graph (§ Call Graph Rules 10).
4. **Exception types are free text.** `Business`, `Business Exception`, `Exception Business`, `Technical`, `Technical Exception`, `Exception Technical`, `System Exception`, `Timeout`, `Action Failed`, `Internal Exception`, localised spellings and a blank type all occur; callers classify with `Upper(ExceptionType())` against a few spellings, and which spellings count as business is what the callers test, not what reads business-like. The source platform raises `Internal` itself for an error no Exception stage raised — a failed action, a missing link, a code stage error *[Inferred from the handlers that test it and the product's error messages]*. Translate the classification ("business when the type reads Business or Business Exception; technical otherwise") and list the spellings once.
5. **Action narratives are stock text.** The `narrative` of an Action on an internal object (Work Queues, Credentials, Collections) starts as the vendor's documentation of that action, copied into every stage; the author's notes are the page narratives (`SubSheetInfo`), the `Note` stages, the stage names, and a narrative the author wrote over the vendor's. `dump` drops a narrative another call of the same action repeats and prints one only this call carries.
6. **Dynamic elements and scripting in code.** A `dynamic` attribute is filled by the calling step's `elementparameter` (an XPath template with the caption substituted, a SAP id with a counter appended, a window title from an argument) — a selector variable, not a literal. SAP toolbar buttons, menu items, grid row selection, layout choice and the transaction call are often done in **code stages** through SAP GUI scripting (`session.findById("wnd[0]/…")`) with no spied element: `profile` § SAP SCRIPTING IDS and `targets` `codeLocators` list them; the genome states the function; the build uses the SAP activities that own it. Never treat a code stage as "code to port" when it drives the UI.
7. **Login Agent is not the process.** `Login Agent` calls (`Get Credential Name`, `Is Logged In`, `Log In`, `Unlock Screen`, `Send Secure Attention Sequence`), a login sub-process, screen-resolution objects and the `Windows Login: <machine>` credential sign the robot into its machine; in UiPath that is the unattended robot's machine configuration. Record, do not build.
8. **Queue names are case-insensitive.** A process spelling a queue `Global-…` where the release defines `GLOBAL-…` uses the same queue; `profile` merges the spellings and lists them.
9. **Queue tags have no Orchestrator field.** Tags are free text a process attaches to items and filters on (`Get Next Item Tag Filter`, `Get Report Data Tags="+X; -Y"`); authors use them as a state machine (the item's source, the phases done, its reporting state, defer counters) and to join child items to their parent. Word each tag by its meaning and flag the realisation `*[Inferred]*` (§ Platform Resources).
10. **The environment lock has no counterpart.** `Acquire Lock` / `Release Lock` around a phase serialises robots; UiPath has no lock primitive, so the build guards the phase with the skill's once-guard. When the source also records the phase in a queue, that queue is the durable part.
11. **Password items are encrypted and never exported in clear.** `password` data items carry an `initialvalueenc`; `Credentials.Get` fills them at run time. The genome names the assets; no value is ever present or copied. **Password items also flow into places a password should not be.** The source platform passes a `password` item transparently into any text input — a `Start Process` command line (`-pw=`), a `Write` into a field, a code stage — so authors sign in to SAP GUI through the shortcut launcher or type the password from code without noticing. In UiPath every such use converts a SecureString to text, which the workflow analyzer rejects at build and which puts the password in the process list for the launcher's lifetime. The genome states the sign-in ("start the application signed in as the account") and names the idiom in the Source Map; execution uses the native login activity of the technology where one exists (SAP GUI has one) and records any remaining conversion as an accepted analyzer finding.
12. **Personal data in literals.** A creator's address in the release header, a person's mailbox in a Send Email input, a user's identifier in a credential name: name the role in the genome, note the deviation in the Source Map, never repeat the value.
13. **Choice "otherwise" branches often throw.** A `ChoiceStart` whose `ChoiceEnd` leads to an `Exception` ("the source is not specified", "the status is not defined") is a closed enumeration: list the cases as the rule and the otherwise as the technical error.
14. **Stage and data item names repeat.** `retry`, `Exists`, `Update Status`, `R` occur many times per process, and every page has its own data items of the same names; so do Block names (two «Block1» on one page, each with its own Recover), which `dump` tells apart by the stages each holds. Refer to pages by name and stages by page and name only in the Source Map.
15. **The configuration file is outside the release.** A process that reads its settings from a workbook, or from a file an object parses, carries only the key names (the fields it references on the settings row) and the sheet or file names, so every key's value is missing from the export, and a key a literal elsewhere gives a value is placed like any literal (the skill's Configuration Questions rules). The environment-variable values (roots, mailboxes, environment name) **are** in the release.
16. **`published` on a page means nothing for a process.** Process pages are `published="False"`; an object's published pages are its actions, the only pages an Action stage of a process or another object can name, and an unpublished page is private to its object, run by the object's own Page stages (vendor documentation) — folded into the action that calls it (Call Graph Rules 5).
17. **A `Process` stage's inputs are the sub-process's contract.** The inputs a caller fixes on a `Process` stage (a login domain, a browser-profile flag) are the caller's values: the domain a Configuration Question, the flag stated in the caller's step (the skill's Configuration Questions rules).
18. **A release may lack what a process needs.** Objects, queues or environment variables a process references but the package omits appear as unresolved callees or referenced-only queues in `profile`; say so in the Source Map rather than inventing their behaviour. A standard object it omits reads as the vendor ships it (§ Internal and stock actions).
19. **Version 6 writes a definition differently.** Its stage geometry is `<displayx>`, `<displayy>`, `<displaywidth>`, `<displayheight>` elements, not `<display>` attributes, so a reader of one form finds no Block on the other and every recovery scope reads as the whole page; the case of some attribute names differs too (`matchindex` / `MatchIndex`). `dump` reads both forms; read the export, never the version number.
20. **A code stage's logic is often in the object's global code.** Its body is one line calling a method of the object's shared code, which the `ProcessInfo` stage holds in `<globalcode>` or `<code>` — one of them, the other empty — with the object's `<language>`, `<imports>` and `<references>`; no code stage declares its own language. `dump --full` prints both, and the genome states the method's rule where the stage calls it. From version 7.4 the language can also be Python, whose global code is a module named `global_code` that a code stage imports, not a class the stages share (vendor documentation; not observed).
21. **Stage, group and element ids repeat across objects.** A page or object copied between objects keeps its stage ids, its `<groupid>`s and its application-model element ids, so an id names a stage or element only within its object, and a `<groupid>` pairs a Loop, Choice or Wait only within its page.
22. **A Resume is a jump.** Its link can lead to any stage of the page — often one before the Block, a retry from the sign-in — and several handlers can link to one Resume and share its tail, so a rebuild in nested blocks needs a flag for each such jump; the page shapes read such a page as a graph (§ Call Graph Rules 10).

Author conventions that recur across releases — patterns to recognise, not rules; a release has its own:

- Size-named sleep and timeout constants (S, M, L …, each a number of seconds) after every launch, save and kill, and a shell `taskkill` plus `Kill Process` before every application launch: timing and cleanup, one Error Handling line each.
- Duplicated export pages differing by a literal (`Start Export <DOC>2` / `<DOC>3`), some unused (Call Graph rule 6).
- Browser objects split by concern (sign-in and lifecycle, list page, record page, browser launch and dialogs), each with its own window elements and an `Attach` page every action starts with — one library per object; an object's window twins collapse into one screen.
- An environment lock around the population phase plus a ledger queue keyed by date recording the phase once (pitfall 10).
- Tags as a state machine: `SOURCE:<application>`, phases done (one tag per transaction exported or document uploaded), reporting state (to report, reported), cleanup (to clean, cleaned), defer counters (`<PREFIX><n>`); `Tag Filter` joins children to their parent (pitfall 9).
- Credentials re-read after a sign-in failure and compared with the ones used, to detect a changed password — a detection rule in Error Handling.
- Grid cells reached by `aria-colindex` / `aria-rowindex` with the header title read first to find the column index; coordinate clicks at the centre of `WebGetBounds` rectangles and clipboard pastes for controls that ignored the DOM click or typed input ([selectors-guide.md](selectors-guide.md) § Web, § Composite actions — worked example).
- `Get Report Data` date windows (`AddDays(Today(), -365)` to report the last year, `-30` / `-10` to clean folders of items finished 10 to 30 days ago) as business rules, stated with their day counts.
- A retroactive-start flag switching the date filter, clearing export folders and closing the browser early — one step with variant substeps, the flag placed per the skill's Configuration Questions rules (a start input goes in Interface), never a second component.
- A first pending item taken and held locked as the **master item** of a workbook, the rest of the workbook's items fetched by a key or tag filter while it stays open: its lock is the claim on the whole workbook.
- A suffix on the resource name selecting test behaviour; a debug flag nothing reads.
