# Framework Pack Contract

What a framework pack in this repository provides and how the `uipath-planner` skill (extraction, which writes the genome) and the `uipath-genome` skill (execution, which builds it) consume it. Extraction runs one pipeline for any source; a pack under `<framework>/` supplies the framework-specific knowledge: `source-guide.md`, `selectors-guide.md` (when the framework records UI locators), `schema.md` (the export shape the script knows), `scripts/` (the inventory script) and `examples/` (worked genomes). A rule or contract of either skill is cited by its subject in the skill's own words (rule 4); the `uipath-planner` skill's guides for UiPath sources are the reference for a source guide's signals. `<PACK_DIR>` in a guide is the root of this checkout; `<SKILL_DIR>` is the folder of the skill running the command (`uipath-planner` for `check-genome.mjs`).

## What a source guide must provide

Every source guide has these sections, in this order, with these headings:

1. **Detection** — file and folder signals identifying framework and unit of deployment. Must distinguish single component from multi-component bundle (solution, release package, project group). Must state fallback when top-level manifest is missing.
2. **Inventory and Exclusions** — file patterns per artifact type; generated, cached, or boilerplate directories and files that must not be read for logic.
3. **Component Detection** — how to recognise each buildable component type and which genome component **Type** and UiPath **Skill** it maps to. This table is the migration bridge: what each foreign construct becomes in UiPath. A `### Layout and names` subsection follows it: the tree the owners navigate the source by (folders, groups, directories) and what each part of an object's path becomes — the project, a folder inside it (the skill's rule that the rebuild keeps the source's names and shape), or nothing — with the inventory field that prints the path, and the names the rebuild takes from the export. A source with no such tree says so.
4. **Signal Tables** — one table per artifact type: `signal | where in the file | what it tells you | example`. Cover: steps/actions, control flow (conditions, loops, switches), error handling (try/catch, retry, on-error paths), arguments and data (inputs, outputs, variables, data items), external targets (applications, URLs, connections, credentials), invocation edges (calls to other components), triggers and schedules.
5. **Target Resolution** — resolving indirect references to the real application or system (connection GUIDs, object references, library names → "Salesforce", "SAP GUI").
6. **Call Graph Rules** — where entry point is declared, how invocation edges are expressed, ordering rules for parallel branches, handling of libraries and unreachable objects.
7. **Expression Translation** — framework's expression language(s) and how operators map to plain language (extends the skill's Business Rules wording).
8. **Platform Resources** — where queues, credentials, assets, schedules, and connections are declared, and their UiPath equivalents for the Platform Dependencies section.
9. **UI Target Locators** — where the framework stores recognition data for the controls it automates (object maps, selectors, XPaths, image anchors), which locator formats occur and how each maps to a UiPath technology, and the command or procedure deriving a normalized target catalog from the export at execution time (the skill's migration preflight; extraction reads it only for control types, actions and counts — the skill's Source Map contract). Attribute-by-attribute translation lives in the companion `<framework>/selectors-guide.md`, one table per technology the framework records (`source field | UiPath tag.attribute | transform | confidence | notes`), right-hand side using only the vocabulary of the skill's selector translation — UiPath-side rules are stated there once, never restated in a source guide. A framework storing none says so; execution then falls back to capture or placeholders.
10. **Test Data** — where data-driving rows live (recordsets, data sheets, variables), how to decode them into named rows linked to the process that runs with them (the data catalog execution derives from the export), which columns are credentials (the skill's Platform Dependencies rules), and the source's execution flags.
10b. **Provenance the Source Map must carry, and the inventory shape** — what identifies the export, what identifies a source object unambiguously (name plus id where names repeat), and the locator a step table's source object carries, `` `Name` (id, <locator>) `` — its position inside the object (lines, a page, nodes, test steps) — so the rows and step tables of the skill's Source Map contract can be filled; and the framework script's command that writes the two files the skill's genome check (`scripts/check-genome.mjs`) reads to check the step tables against the export — process inventory (`[{id, name, recordset, calls: [{calleeId, recordset}]}]`) and recordset list (`[{id, name}]`; an entry with `drives: false` is provenance, never a data set). The check is framework-agnostic and reads no export; only the framework script does.
11. **Evidence** (frameworks with blanket screen captures or result logs) — which step kinds count as checkpoints for the Source Map's Checkpoints row and how the source's own result log reads; which commands write the run's log and which files hold it, told apart from the engine's own per-step record, so every source log line is rebuilt and each log file goes where the skill's evidence policy puts it (the skill's table of source steps that are not UI actions); the generic policy: the skill's evidence policy.
12. **Framework Pitfalls** — anything that misleads a reader: designer metadata that looks like logic, generated code, duplicate definitions, version-specific quirks. A pitfall restating a generic rule points to it instead.

## What the inventory script must provide

One script under `<framework>/scripts/`, run before any export file is read, with the commands `profile` (identity, vocabulary, call graph, roots), `cards` (one compact card per source object), `dump` (one source object in execution order), `raw` (§ Reading the source directly; a source in code has none), `targets` (the UI target catalog: controls with parsed locators and the actions applied), `data` (the process inventory and data sources § 10b names) and `check` (a renderer completeness self-test: every value a source object carries — typed literals, flags, nested options, bindings — appears in that object's `dump` line and in every curated rendering of it: its card, its catalog entry, the configuration section, the data catalog; non-zero exit on a miss). A curated rendering loses values more easily than a raw one: an option parser that reads only flat values, a cut at a fixed length, a list of the settings worth keeping (a catalog keeps a command's settings by denylist, never by allowlist), a chain whose parent scope is not carried, a value or a list printed through the language's own representation or JSON's escapes outside a JSON output (both re-escape every quote and backslash; a text rendering prints a value as written, a character a reader cannot see as `\uXXXX` and a backslash that would start one as `\u005C`, so that every `\uXXXX` it shows is one character — and encodes it once, since a second pass turns the first one's `\uXXXX` into text) — `check` covers every surface the extractor or the executor reads, and tests each as written. When the source format has an authoritative parser (a language's compiler, a schema), `check` is validated against it once whenever a renderer changes: the values the parser reads per call are the ones `check` must find. Every writing command takes `--out <DIR>`; `dump`, `raw` and `check` print to stdout. A source format stores values in typed channels (a number, a boolean as text, an expression) and nests options; `check` is what keeps a curated rendering from silently dropping one, and it is run on every export before the dump is read. The script never prints a secret: values of variables, attributes and environment variables whose names match password / pwd / secret / token are masked. Enumeration values that name an action or a mode (the verb of a type-into, the mode of a parsing step) are never secrets, whatever attribute or variable name they sit beside — masking them hides behaviour, not a credential. The source guide's command block at the top shows every call for extraction and for the build with `<PACK_DIR>`, `<EXPORT_DIR>`, `<WORK_DIR>` and `<BUILD_DIR>` placeholders.

Where the export names work queues, `profile` lists per queue the processes that add, take, change and read its items, an action that names no queue counted under the queue its item id is traced back to, and listed apart when the trace reaches none.

`dump` addresses a source object by its id — a name is accepted only when it is unique, or prints every copy under its own id, because a lookup by name that returns one copy hides the others; every catalog names an object by name and id for the same reason. The secret masking covers free text the recorder or the author wrote around a value as well (a step narrative, a comment, a description): a masked field whose literal reappears in the narrative is still printed otherwise. `check` covers the `targets` catalog the same way: every recorded locator value and every non-mechanical parameter of a live UI step appears in its control's entry. Where the format makes the count exact, `check` also confirms that the process inventory's call list of each object equals the invocations in that object's own body, so objects named alike never share edges.

A format whose control flow is jumps between steps (pages of linked stages, labelled gotos) has `data` also write a **shape catalog**: per flow, `blocks` when it has a block-structured reading with no added control variable and no step written twice, otherwise `graph` with the reasons, and its steps with their positions on the source canvas, its links and its recovery regions. The source guide's § Call Graph Rules says how it reads; `check` builds each flow again from the export and compares. A format whose flow is structured, or a dataflow of connected nodes, writes none.

`check` derives what it expects from the raw export, never through the renderer helper it is testing: a helper that reads the wrong channel or pairs cells with the wrong row would otherwise drop the value from the rendering and from the expectation alike, and pass. It also covers the export's shape against `<framework>/schema.md`, one table row per typed key path (a data format) or per API member on a typed receiver (a source language), each `rendered`, `structure`, `ignored`, or `ignored while` its default values; the first row whose pattern matches decides, and `*` is the only wildcard. A path holding a value that no row documents, or a flag outside its documented default, is a finding like a missing value: a new export version or a feature the fixtures never used reaches the pack as a report rather than passing unread. A new finding is resolved by rendering the value, or by adding the row with the reason it can be ignored — never by widening a pattern until it swallows the path.

### Reading the source directly

Every rendering is the script's reading of the export. A finding that the source misbehaves rests on one, so extraction checks it against the source itself before the genome calls it a defect (the skill's verification of suspected source defects). The source guide states how, next to its command block.

- **A structured export** (JSON, XML, a database dump) gets a `raw` command. It prints the objects a finding cites, by the identity `dump` prints for them (a line or step number, a stage name within its page) or by a text they hold, and the declarations and test data they read (a variable, a data table's rows, the filter a call applies to them), as the export holds them. Every key is kept. Left out are only empty values, the defaults every object repeats and binary blobs (their size stays); keys are dropped by that denylist, never kept by a list of fields worth reading. A reader that names the keys it keeps hides whatever it did not name, such as a chained condition under its own key or a result bound on the node, and the discrepancy it then reports is its own. `raw` reads the export afresh and counts lines itself: it shares nothing with the renderers but the object lookup and the secret masking, which is the renderings' own. It is a lookup, never a way to read a whole object.
- **A source in code** is its own raw form: the finding's lines are read in the file. The source guide names what is never opened (a file of environment secrets) and which lines are read through `dump` only (a line it masks).

## Rules

1. **Signals, not procedures.** A source guide tells the extractor what to look for and what it means. The pipeline (inventory → signals → call graph → mapping → write) stays in the skill's extraction guide.
2. **Every construct maps to a UiPath skill.** The Component Detection table must name a skill from the `uipath-planner` skill's Build With mapping for every buildable construct, with a one-line rationale. A construct with no UiPath equivalent maps to the nearest skill and the genome flags the gap with `*[Inferred]*` in Build With.
3. **Behavioural output only.** Nothing in a source guide licenses activity names, object names, or variable names into the genome body. They may appear only in the Source Map.
4. **Self-contained.** A pack links only inside its own folder and to this file. A UiPath-side rule or contract stays in the skill that owns it (`uipath-planner` for extraction and the genome format, `uipath-genome` for execution); *the skill* is the one reading the section — `uipath-planner` for a source guide read whole at extraction, `uipath-genome` for the sections a build reads (§ Composite actions, § UI Target Locators, § Test Data, the selectors guide) — and a cite of the other skill names it. A rule is cited by its subject in the skill's own words — "the skill's rule that one tag is one node", "the skill's Source Map contract" — never by a file name, a section mark or a rule, step or item number: the pack is read beside the skill, whose read plan opens the skill's files, and the skill reorganises its files without the pack. The skill's scripts are commands and keep their names (`check-genome.mjs`). The skill never reads a pack file by a hardcoded path.
5. **Placeholders, not customers.** Observations are described by technology (Java Access Bridge, SAP GUI, HTML); an application appears only as the worked example of a technology, and bot, process, vault, variable, host and account names in examples are placeholders.
6. **Capability level, not class level.** A pack states what the export contains and what a construct corresponds to as a capability — type-and-confirm, read control text, menu path, kill a process, a credential read inside the scope that types it. It never names a UiPath activity class, a property or its value encoding, an analyzer rule code, a package pin or expression-language code: the build fetches those at the version it builds against (the skill's build contract) and records what it chose in that build's migration report (what the skill's executor records); a written copy is stale on the next package bump and nothing says so. Activity display names (Type Into, Click, Get Text) are capability vocabulary and allowed. The one exception is the selector tag and attribute vocabulary of the skill's selector translation, which a selectors guide's right-hand side must use (§ 9) — the skill's catalog is its single authority, and a pack never decides between two spellings of an attribute; it names the catalog entry.
7. **Generalise before writing.** Each fact is true of the framework's export format wherever it is produced, true of a technology whatever framework recorded it (an XPath's id belongs to the step that carries it; a Java Access Bridge grid is rows of same-named text fields), or true only of the corpus it was measured on. Only the first two enter a pack, each filed under the thing it is true of — a technology fact is worded so the next framework driving that technology can reuse it; a corpus fact is at most an example or a Configuration Question, and a customer's own package semantics never enter at all. No measurement counts, corpus references, node ids or versions: say what is confirmed and what is inferred, never where it was seen.
8. **Name the source platform once.** A guide or schema names its platform, vendor and product, in its title and, where a term needs a definition (a product line, a version number, a word such as *native*), once in a note at the top: legal guidance keeps platform names out of the running text. Elsewhere it says *the source platform*, *the vendor* for the company, and *Source* in a table header (`Source platform | UiPath`). Bare *the platform* means UiPath in some of the skill's rules and the source in others, and execution reads a guide by section, so each sentence says which side it means without the note. Names that are data stay as written: file names and paths, packages, node types, API members, element and attribute names, an object's or a command's exact name, and a product's own short name (`Desktop`, `Control Room`). UiPath is always named.

## Adding a framework

1. Create `<framework>/` (lowercase kebab-case vendor and product) and copy the section skeleton above into `<framework>/source-guide.md`.
2. Fill Detection first; the skill cannot select the pack without it.
3. Add a row to [README.md § Frameworks](README.md) (detection, folder, script commands) — the single place extraction and the build both look up a framework.
4. When the framework records UI locators, add `<framework>/selectors-guide.md` (formats, then one translation table per technology) and survey real exports before writing it — attribute names come from the data, not the vendor's documentation.
5. Add the inventory script under `<framework>/scripts/` per § What the inventory script must provide, and `<framework>/schema.md` from a survey of real exports: `check` passes on each of them with no undocumented path.
6. Add one worked example under `<framework>/examples/` extracted from a real project of that framework, with a Source Map, neutralised per rule 5.
