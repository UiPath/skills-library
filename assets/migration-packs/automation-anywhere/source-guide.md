# Automation Anywhere Source Guide

> **The source platform** is Automation 360. A **native** bot, or one authored **natively**, was built in it rather than migrated from Enterprise 11.

Framework facts for extracting a genome from a **bot export** — bots authored natively (a Control Room "Export bots" package with a `manifest.json`) and bots migrated from Enterprise 11 by the Bot Migration wizard. Follows [CONTRACT.md](../CONTRACT.md); pipeline: the uipath-planner skill's extraction; generic rules pointed to below are not restated here. Observations come from production exports of both kinds — bots migrated from Enterprise 11 and bots authored natively — driving a Java desktop application (Oracle Forms through Java Access Bridge) with a browser launch page, from a mailbox intake, a REST intake and a SQL Server process database. Oracle Forms is the worked example of the `JAVA` technology below, not a property of the framework; bot, vault and variable names in the examples are placeholders.

Export = a folder tree mirroring the Control Room repository: `Bots/My Tasks/<folders>/<BotName>` (or directly `Bots/<folder>/<BotName>`) and `Bots/My MetaBots/<folders>/<BotName>` hold one **extension-less JSON document per bot**; `<BotName>Metadata/` folders hold the recorder's screenshots; files the bots read through `repository:///` URIs lie under `MyDocs/` (or `My Docs/`) or beside the bots in their own folder; a Control Room export adds `manifest.json` beside the `Automation Anywhere/` tree. Bot documents are small (tens to hundreds of kilobytes) but a bot line holds a base64 blob per captured UI object and the same twenty- to hundred-variable dictionary on every sub-bot call, so read them through the bundled inventory script, never raw — a finding is checked against the file itself through the script's `raw` lookup, never by opening or printing the file:

```bash
# Extraction (`uipath-planner`) — read the export from a scratch folder
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py check   "<EXPORT_DIR>"                      # renderer self-test, first: non-zero exit = a rendering hides a value this export carries
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py profile "<EXPORT_DIR>" --out "<WORK_DIR>"
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py cards   "<EXPORT_DIR>" --out "<WORK_DIR>"
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py dump    "<EXPORT_DIR>" <BOT_ID> --compact   # one bot, line by line; drop --compact to see disabled subtrees in full; a name is accepted only when it occurs once
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py raw     "<EXPORT_DIR>" <BOT_ID> --lines <FROM>-<TO>   # the file's own nodes at dump's line numbers (or --find TEXT, --var NAME), to check a finding against the source
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py targets "<EXPORT_DIR>" --out "<WORK_DIR>"   # windows + captured controls with decoded properties, the action applied and every setting
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py data    "<EXPORT_DIR>" --out "<WORK_DIR>"   # bot inventory with call edges + data sources, for the Source Map check
# Build (`uipath-genome`), migration preflight — derive the catalogs into the build's working folder
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py check   "<EXPORT_DIR>"
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py targets "<EXPORT_DIR>" --out "<BUILD_DIR>/migration/source"
python3 <PACK_DIR>/automation-anywhere/scripts/a360-export-inventory.py data    "<EXPORT_DIR>" --out "<BUILD_DIR>/migration/source"
```

`profile` writes identity, manifest cross-check, packages, folders, command vocabulary, per-bot summary, call graph, roots, credential references, windows, capture counts, application launches, API calls and DLL functions, stored procedures, mail, database and file commands, evidence density, migration plumbing, the variables read but never assigned under any spelling (no default, not an input, no enabled command stores into them — a set-title stores into the window variable it rewrites: every read is empty — a result its command does not store, a name nothing fills), the inputs a call leaves unbound (the callee reads the input and never assigns it, it has no default, and the call binds no spelling of it — the callee reads it empty; a compact dump folds the bindings a call has, never the ones it lacks) the variables written in several spellings (one variable each: § Value syntax), the catch results a call does not receive (an output the callee's catch stores and no later line of the callee reads — its error status, its reason — that the call binds back under no spelling: the caller never learns of that failure) and the tests an enclosing test rules out (an `if` or `elseIf` whose string test contradicts an enclosing arm's string test, alone or joined by AND, on the same variable, with no store into it that can reach the nested test — the arm never runs); `cards` one compact card per bot (description, inputs, outputs, callers, callees in order with the **real parameters** — bindings that are not a same-named pass-through, and results kept under another name (`<output> -> $variable$`) — windows, captures, conditions, loops, database, API, keystrokes, error handling with a `throw` inside `finally` and the calls to such bots inside a loop that tests what they return (§ Signals — Bot, `ErrorHandler.try`), evidence); `dump` one bot in editor order with every attribute rendered (a `break` or `continue` also names the loop it acts on — `break (leaves the loop at <line>)`, `continue (next pass of the loop at <line>)`; an Extract text the part it keeps — `[= text after "/"]`, § Value syntax; a loop its form, its pass limit and a capture before it that its body repeats — `[tests before each pass; at most 15 passes: line 151 breaks out when $Loop-Counter-2$ = 15; line 142 runs before the loop and again at 148 inside it: up to 16 times]`, § Signals — Bot, the `WHILE` row), then a VARIABLES legend — every variable with its type (a session variable with its package, `SESSION(Excel_MS)`), interface flags and default, a table, list or record default included (a header table kept as a variable default is the data contract the bot writes) (`--compact` folds disabled subtrees to one line, folds same-named pass-through bindings of a sub-bot call to a count, renders a call to a **logger bot** as a log line, and leads a log line with its message and target file and a delay with its time, every other setting following — a log into a business file is a data write, and whether it overwrites or appends is part of it). `dump` takes the bot's id (or its repository path): a name is accepted only when it occurs once, and a repeated name lists the copies. Every value is rendered from the channel its type names — numbers, booleans (`[matchCase]` / `[ignoreCase]` on every string condition or table search that states its case rule), options nested under a choice, the settings a dedicated shape does not name — and no rendering cuts a value at a fixed length or escapes it (§ Value syntax); `check` proves it for the export at hand on every surface: each node's `dump` line and, when enabled, its line in the compact dump as printed (a command label is the node's own `Package.command`; a fold that swallows a live line is a miss — a disabled arm folds its own body, never the arms after it; so is a call printed as a log line whose results the caller binds), the VARIABLES legend, the card items that carry a node's line, the real parameters of every sub-bot call and the card's window titles, the `targets` entry of every capture, keystroke and window command (every setting) and window variable, and the `data` entries in the JSON and the `.md` (call bindings, the recorded attributes of every data-bearing command), each data source's name citable and named by no other source of its kind (§ Test Data); a reading taken from a rendering that `check` fails on is not a source fact. `check` also compares every key path holding a value with `<PACK_DIR>/automation-anywhere/schema.md`: a `schema` finding names a path no row documents (a newer Control Room, a command feature the pack has not met) or a flag outside its documented default, with the bot and the value — no rendering shows that key, so its meaning is inferred from the path and the value, or asked as a Configuration Question, and it is reported for the pack. The card is an index, the dump is the source. A logger bot is a bot whose only effect is its log lines: made only of log, flow and string commands (the log's own file or folder created), with at least one log line, no sub-bot call and no command storing into a result — a variable flagged output only, or one a call binds back (a variable flagged in and out that no caller receives is the bot's own working state, the flags migrated bots set on everything); `profile` names them and every catalog flags them — their calls are the run's own logging, never steps. A helper that copies files or hands a result back is a step, whatever commands it is made of. Read profile and cards in full; dump every bot the genome covers — compact first, full only where a folded subtree matters. `targets` writes the UI target catalog (`a360-targets.json` + `.md`: window variables, captured controls with decoded object properties, keystroke and window commands, each with every setting its command carries — § UI Target Locators); `data` the bot inventory (`a360-process-data.json`, a **list** with id, path, folder, inputs, outputs, call edges with their argument bindings) and the data sources the bots read and write, each named as a step table cites it (`a360-data-sources.json` + `.md` — § Test Data). Which mode reads what, and why nothing is written beside the genome: the skill's Source Map contract and its migration preflight.

`raw` is the source itself, for checking a reading against the file rather than against a rendering (the skill's verification of suspected source defects). It prints the bot's nodes at `dump`'s line numbers (`--lines`), or the nodes whose command or JSON holds a text (`--find`), and a variable's declaration (`--var`), as the file holds them. Every key is kept. Left out are only empty values, the defaults every node and value repeats (`disabled: false`, `taskbotSelf: false`, `securelyRecorded: false`, `repository: false`, `sessionTarget: NONE`, an `operator` of `NONE`) and the recorder's blobs, whose size stays. The empty channel a scalar's type names is kept, so an empty literal reads as set to empty, not as unset. Secrets are masked as in every rendering. The lines are counted afresh from the file: a node is marked `[off]` when it is disabled itself and `[off by parent]` when an ancestor is, and a line ends with its body's span and its branches' lines (`body=3-35 branches=catch@36,finally@39`). `raw` is a lookup of the lines a finding cites, never a way to read a bot. When the rendering and `raw` disagree, report it for the pack with the bot, the line and the key.

Exports carry no numeric object ids: a bot is identified by its repository path, and names repeat across folders (`Main` in two projects, a MetaBot logic and the task that calls it named alike). The script derives a stable six-digit id from the path (CRC-32 folded into 100000–999999; the same export yields the same ids) so Source Map rows carry `` `Name` (id) `` and `check-genome.mjs` resolves the step tables' citations.

## Detection

| Signal | Meaning |
|---|---|
| Folder containing `Bots/` whose files are extension-less JSON documents with top-level `nodes`, `variables`, `packages` (and `triggers`, `breakpoints`, `properties`, `migrationJournalReviewIds`, `workItemTemplateName`) | Control Room export. Multi-component: a repository folder holds a **root task bot plus the sub-bots it runs**, so the export is a **process genome** whose components are the bot groups of § Component Detection. |
| `Bots/My MetaBots/…` folders | Enterprise 11 MetaBots converted by the Bot Migration: their logic blocks are now ordinary bots, each still one reusable UI capability |
| `Bots/My Tasks/…` folders, or process folders directly under `Bots/` | Task bots (v11 `.atmx` converted, or authored natively) |
| `<BotName>Metadata/` beside a bot, full of `*.png` | Recorder screenshots (`screenshotMetadataPath` / `thumbnailMetadataPath` inside capture and region values); evidence of what was captured, never logic |
| `migrationJournalReviewIds` non-empty, `LegacyAutomation` package, variables named `m-*` / `M-*` / `Loop-*` / `Error-*`, `Prompt-Assignment`, `my-list-variable` | Bot Migration output: the bot was converted from Enterprise 11 (§ Framework Pitfalls) |
| `manifest.json` beside the `Automation Anywhere/` tree: `files[] {path, contentType (application/vnd.aa.taskbot, image/png), scannedDependencies[], manualDependencies[], metadataForFile, excluded}`, and — not always present — `description`, `author`, `packages[]` | A Control Room **bot export** package (native bots, or a mix): the file list is the export's identity, `scannedDependencies` are the enabled Run Task targets **and the repository files** the Control Room found the bot referencing (DLLs opened, configuration and state files read, scripts run), `manualDependencies` what the author added by hand — a file dependency or a manual one is not a stale call edge (`profile` § MANIFEST cross-checks the bot dependencies against the bots' own edges and lists file and manual dependencies apart), `metadataForFile` ties each screenshot to its bot; `excluded: true` marks a bot the exporter left out. **The manifest may list dependency files the package does not contain** — configuration XML, state files the bots write back, the DLLs of scripting wrappers, scripts (`profile` § MANIFEST names them): their values and code are then outside the export, and every setting read from such a file is a Configuration Question without a default. Absent on Bot Migration output |
| Empty `migrationJournalReviewIds`, a first `Step` block titled `Comment Section` with `Description :`, `Author :`, `Created Date :` comments, variables prefixed `v` / `i` / `c` (value, input, constant), `Step.step` sections naming each phase | Native authoring. The section titles and `Description :` comment are the author's narration — a wording source to **verify against the steps**, not to copy: in a native export they are often pasted from bot to bot and describe another bot's purpose; the log-line text and the captured object names are the reliable narration. **Detect Enterprise 11 origin per bot, not per export**: a migrated bot copied into a native folder keeps the `LegacyAutomation` package, the `m-*` / `M-*` / `Loop-*` variables, the `parseVariableOperation` re-assignments and the `finally` / throw idiom while its journal ids are cleared — the plumbing says v11, the empty journal says nothing |
| `$@AAE_EnvironmentType$` or `$System:AAControlRoom$` compared to `dev` / `uat` | Environment switch: the bot picks connection strings, URLs and credentials by the Control Room it runs on → Configuration Question "which environment" and one asset per Orchestrator folder |
| `packages[].version` | Package build dates identify the source platform release the export was taken from (e.g. `Recorder 2.16.0-20231101-…`) — the version the Source Map states |
| `properties.automationPriority`, `properties.botCodeVersion` | Run priority and the bot's own edit version; identity only |
| `MyDocs/*.xml`, `MyDocs/*.xlsx`, or `.xml` / `.xlsx` / `.vbs` files beside the bots | Configuration files, templates and scripts the bots read through `repository:///` paths; the only run-time data present in the export |

A single bot file with no `runTask` command is one **component** (component genome). An export missing `Bots/` but holding the JSON documents in one folder is still an export; the repository paths are then the file names, flagged `*[Inferred]*`.

## Inventory and Exclusions

| Pattern | Contents | Use |
|---|---|---|
| `Bots/**/<Bot>` (no extension, JSON) | One bot: `variables[]`, `nodes[]`, `packages[]`, `properties`, `triggers[]`. **Document order is execution order**: `nodes[]` is a tree whose `children` are a node's body and whose `branches` are its `else` / `elseIf` / `catch` / `finally` arms **as full nodes** — each with its own `uid`, `attributes` and `children`, never a `{nodes: []}` wrapper. Nothing is unreachable except through `disabled`. A `uid` is unique inside a bot only: bots copied inside the Control Room (`_V1` / `_V2` pairs, MetaBot copies) keep the same uids, so a node is identified by bot id + editor line (§ Provenance) | Steps, control flow, call graph, interface, targets |
| `nodes[].variables` … `variables[]` fields `name`, `type` (STRING, NUMBER, BOOLEAN, LIST, DICTIONARY, RECORD, DATETIME, WINDOW), `subtype`, `input`, `output`, `readOnly`, `defaultValue` | Bot interface (`input`/`output` flags) and constants (`readOnly`, literal defaults); WINDOW variables carry the recorded window (`window.name` title with `*` wildcards, `window.class`, `window.path` executable) | Interface, Target Applications, target catalog |
| `<Bot>Metadata/*.png` | Recorder screenshots of captured controls and screen-change regions | Evidence only; never read for logic |
| `MyDocs/`, `My Docs/`, or non-bot files in a bot folder | Configuration XML, workbooks, templates and scripts addressed by `repository:///Automation Anywhere/Bots/…` URIs | Values placed per the skill's Configuration Questions rules; data sources |
| `triggers[]` | Bot-level triggers (empty in exports of scheduled bots — schedules live in the Control Room, not the export) | Deployment note |

Excluded from logic: nodes with `disabled: true` **and their whole subtree** (the editor shows them greyed; the runtime skips them — `dump --compact` folds them to one line; the descendants of a disabled node are dead **whether or not they carry `disabled` themselves**, and most do not, so a per-node test misses them — the script propagates the flag before anything counts); `Comment` nodes whose text is a separator (`====`, `----`, `||||`) or a migration placeholder (`Please enter the commands to handle errors.`, `EndIf`, `Please enter the conditional commands here.`); `MessageBox` nodes (debugging left-overs — in a production export they are almost all disabled; an enabled one is a pitfall, § Framework Pitfalls); `LegacyAutomation.getKeystrokesDelay` (computes the delay the following keystroke command uses); `Delay.delay` as a step of its own — its **value is not excluded**: a fixed pause is kept at its value and unit with the step it precedes or the retry it spaces ("wait 60 s, then try the write again"; the skill's table of source steps that are not UI actions); `LogToFile.logToFile` into the run's own log (§ Evidence; its **message text** is the author's step narration and is read for wording) — the command writes text to any file, and a write into a file of the process's own data (a list or dump a later step reads) is a step (§ Signals); `Screen` package commands (screenshots — § Evidence); `String.assign` of a `m-string-start-in-path*` variable (migration plumbing that feeds the next command's path); `.LegacyAutomation:parseVariableOperation` self re-assignments (`$X.LegacyAutomation:parseVariableOperation$ → $X$`) that **immediately follow a literal assignment** to the same variable — the migration inserted one after every v11 assignment and on a literal it is a no-op; the same re-assignment after an expression, or standing alone, may resolve variable references inside the text (the operation's contract is not in the export) and stays a Source Map note on its step; `TaskBot.runTask` of a **logger bot** (the run's own logging — the message binding is the narration, read it like a `logToFile` line); `Credential.assignToCV` (moves a vault credential into a variable for the capture that types it — credential plumbing, the vault reference is what counts); `String.replace` of `$System:AATaskName$` with a path regex (the bot computing its own name for the log); `System.systemInformation USERNAME` (the runner's identity); `Application.runApp taskkill.exe` (§ Step vocabulary); `Database.connect` / `disconnect` around the procedure and query calls (session plumbing — the procedure or query is the step; connects and disconnects need not pair — a session opened once is often closed at every exit); `Number.assignToNumber` of a fixed delay (plumbing — its value is the pause's, carried with it).

## Component Detection

The source platform has one artifact type: the bot. Components come from the **repository folders and the call graph**, not from file types:

| Construct | Component type | Skill | Rationale |
|---|---|---|---|
| The root task bot (never called by an enabled `runTask`) plus the task bots in its folder that only it and its siblings call (initialisation, mail intake, data filtering, navigation, notification, cleanup) | One **RPA process** (REFramework-style: initialise → get work → process → report) | `uipath-rpa` (Process project) | One deployable unit in the source platform (the root is what the Control Room schedules); the sub-bots are its phases, not products of their own |
| A `My MetaBots/<Product>/<MetaBot>` folder: the logic blocks of one migrated MetaBot (login, navigate, search, change a value, read a popup, read a title) | One **UI library** for that application | `uipath-rpa` (Library project, one public workflow per logic bot) | A MetaBot is the source platform's reusable application library; its logics are invoked from several task bots with a fixed argument set (the MetaBot input/output variables) |
| A `Reusable_Components` (or `Common`, `Shared`) folder of bots called from several processes' roots — application launchers, shared exception handlers that mail or record the error | One **common library**; a bot whose only work is the run's log file is the evidence policy (§ Evidence) | `uipath-rpa` (Library project) | The customer maintains it as shared code; other processes of the export or of the tenant depend on it |
| **Copies of a MetaBot kept in the process folder**: generic application bots (enter credentials, change a context value, press a toolbar button, common screen navigation, popup handlers) whose disabled `runTask` commands still point at `My MetaBots/<Product>/<MetaBot>/…`; and a **natively authored generic bot** with no MetaBot trace that several screen bots call for the same application-wide job (a popup handler) | One **UI library** for the application, shared with the other processes that drive it | `uipath-rpa` (Library project) | The bots were copied out of the MetaBot into the process; the dead calls prove the origin. Membership is decided by what the bot does and who calls it — application-generic and called by several screen bots → library — not by its provenance *[Inferred]*. The process's own business screens stay in the process even when they are task bots beside the copies — their rules are the process's, only their popups, toolbar and navigation come from the library *[Inferred]* |
| A **scripting-wrapper library**: a MetaBot folder whose logics each load one compiled assembly (`DLL.Open` once per session) and expose one verb — find the element by its scripting id, click, press, type, read text, select, choose a list entry by key, press a key, maximise, run a script statement — with the element's identity passed **as an argument** (a SAP GUI scripting wrapper is the worked example; a browser or Office scripting wrapper has the same shape) | **Not a component.** Each verb call is the UI action it names, a step of the calling bot's component; each identity passed to it is a UI target of that step | `uipath-rpa` (the calling component's UI activities) | The wrapper is the customer's substitute for a driver; UiPath drives the technology with its own driver, so an element addressed by scripting id is an Object Repository element like any other and the verb is the activity (click, type into, get text, select item, check, keyboard shortcut, the technology's own activities for transactions, status texts and toolbars — § Realised at execution). `targets` lists the identities per caller as `scriptedTargets` (§ UI Target Locators): they are the target catalog of the calling steps, not arguments of a library. The wrapper's session attach becomes the application card's attach to the session window; its "find by name" becomes a selector on the identity's stable tail; its "run a script statement" verb is replaced by what the statement did (select a grid cell → the table read it prepared). The logon bots around the wrapper (portal, certificate) remain workflows of a common library when several processes call them (row below). The assembly, shipped in the export (`profile` § FILES) or not, is compiled code the pack does not read; the verbs' contracts are their parameter names |
| A **generic sub-bot copied into several process folders** (the same logon bot under each process, line for line) | One workflow of the shared library, placed with the technology it drives | `uipath-rpa` (Library project) | Copies are one workflow; diff them and carry **every** difference (a configured window title in one copy, a literal in the other; different wait timeouts) as an argument — diff dumps that `check` passes, never a rendering that blanks numbers. The process folder is where the customer kept it, not where it belongs *[Inferred]* |
| Commands of a **customer-built package** (§ Signals — Bot) that several roots call for run plumbing — robot environment setup and cleanup, drive mapping, a document store | One **common library** of the commands the rebuild has to write (the skill's rule that shared behaviour is one library component); a command one or a few UiPath activities perform is steps of the calling component (the skill's rule that wrappers are not components) | `uipath-rpa` (Library project) | The customer keeps the package as shared code for every bot, so its UiPath counterpart is one library, not a copy per process. The package's code is not in the export: the library genome states each command's contract from the parameters its callers bind and the package values they read, and flags the logic `*[Inferred]*`. A package only one root calls → steps of that component |
| A **logger bot** (log-level filter writing one line per call; § Evidence) | Not a component | — | Evidence policy of the process that calls it |
| `DLL.Open` + `DLL.RunCSharpDLL_V1` (a C# assembly loaded from a configured path, one function called with typed parameters) | What the function does decides, read from the call — its namespace, class and function names, its parameters, what later lines do with its result. One whose work one or a few UiPath activities do (a range copied between workbooks, a cell set, a file copied) is steps of the calling component (the skill's rule that wrappers are not components); any other is a **coded step**, and a function several roots call is one **common library** workflow (the skill's rule that shared behaviour is one library component) | `uipath-rpa` (coded workflow or Invoke Code inside the process project, or Library project) | The assembly ships in the export when `profile` § FILES lists it, and is outside it otherwise; either way it is compiled code the pack does not read. The genome states the function's contract (inputs, output, side effects) from the call and flags the logic, and the choice between activities and a coded step, `*[Inferred]*` for the rebuild |
| `Rest.restPost` / `restGet` chains (token, data, acknowledgement) inside a task bot | HTTP steps of the calling component | `uipath-rpa` (the intake is one phase of the root bot); `uipath-api-workflow` only when the calls stand alone with no UI or file work around them (the skill's Build With decision tree for HTTP calls with no UI) | |
| Bots reachable only through **disabled** `runTask` commands, or referenced by a path no file in the export matches | Dead calls / unresolved | Source Map only | Superseded copies (`<Bot>` beside `<Bot>Task`, `<Bot>` beside `<Bot>_V1`) or bots outside the export (the MetaBot originals) |
| `triggers[]` with an event or schedule trigger | Entry point of the process component | Deployment → triggers | Rare in exports; the Control Room schedule is the usual trigger and is not exported |

Every construct maps to `uipath-rpa`: the source platform has no flow, agent or API-workflow equivalents in an export; a `runTask` chain is workflow invocation, not orchestration. When a root does nothing but call other roots each with its own schedule, consider one process per root and a coordinating Flow `*[Inferred]*`.

### Layout and names

The export is the Control Room repository, and its owners find a bot by its path. When the run keeps the source's names and shape (the answer to the skill's Source fidelity question), execution takes each bot's path from the process inventory (`path`, `folder`, and `calleePath` on each call) or its `dump` header:

| Source platform | UiPath |
|---|---|
| Folders above a component's root — the deepest folder holding all of the component's bots of one tree (`My Tasks/<Customer>/<Area>/`) | No folder; the Source Map names them |
| The component's root folder | The project § Component Detection decides |
| A bot's folders below that root | Folder of its workflow |
| Bot name | Workflow file name as written. Names repeat across folders, and the folders keep same-named bots apart |
| Copies and variants merged into one workflow (Call Graph Rules 10, the copy rows of § Component Detection) | One file at the path of the copy the callers keep; the other copies are Source Map rows of the same step |
| A component drawing bots from several trees (MetaBot logics and a `Reusable_Components` folder in one library) | Each tree's bots below a folder named after that tree's root |
| `Step.step` titles | Display names of the sequences they head |

## Signals — Bot

`profile` and `cards` surface these; `dump` shows them per line. Line numbers are the editor's (every node including `else`, `elseIf`, `catch`, `finally` branches counts one line) — the `Error-LineNumber` a catch block logs refers to them.

| Signal | Path | Tells you | Example |
|---|---|---|---|
| File path below `Bots/` | export tree | Bot identity and folder (process vs MetaBot vs shared) | `My Tasks/Demo/InvoiceMailIntake/MainTask` |
| First `Comment` node, or the first comment starting `Description:` | `nodes[0..]` | Author's purpose statement; verify against the steps | `Metabot logic to sign in to the ERP portal` |
| `variables[]` with `input: true` / `output: true` | top | Bot interface. **Migrated bots flag almost every variable in/out** because the v11 runtime shared them, and native controllers flag every setting; the real contract is the subset the callers bind in `taskbotInput` / `taskbotOutput` — read the call, not the flags. The flags are still the callee's own claim: where they disagree with the bindings (an `output` nobody reads, an `input` nobody binds) the Source Map says so. `inputRequired` is absent in practice and `description` rarely filled — neither is a wording source | |

### Value syntax

`$name$` a variable; `$name{key}$` a dictionary or record field (`$Loop-Email-Response-1{emailSubject}$`, `$Loop-Files-1{extension}$`); `$name[0]$` a list element or a record column by index; `$name.Package:function$` a value transform (`.String:toNumber`, `.Number:toString`, `.String:uppercase`, `.LegacyAutomation:getIncrementedNumber`, `.LegacyAutomation:getCellByIndexOrName("SenderEmail")`); `$@Name$` a Control Room **global value** (`$@AABasePath$`, `$@AAE_EmailSettings_host$`); `$System:Name$` a system variable (`AATaskName`, `Year`, `Month`, `Day`, `Hour`, `Minute`, `Second`, `AATaskExecutor`). A STRING value carries `expression` when it references variables and `string` when literal; read `expression` first. A `string` literal is never substituted, even when its text has a variable's shape — a replace whose find text is `$name$` looks for a template's own placeholder, not for the variable's value — and `dump` prints such a literal as `literal"…"`. The script's text renderings (`dump`, `cards`, `profile`, the `.md` catalogs) print a value as written, in quotes where they quote it, and escape nothing but invisible characters, written `\uXXXX` (`\u000D\u000A` a line break, `\u00A0` a non-breaking space): `"$RootPath$\Archive\"` ends in a backslash, and a `\n` the author typed into a pattern is those two characters. A backslash before `u` and four hex digits is written `\u005C`, so every `\uXXXX` is one character: `\u005Cu00e9` is the six characters `\u00e9` as typed. Comments and descriptions are free text, their line breaks ` / `. The JSON catalogs and `raw` keep JSON's escapes; a setting or binding in a JSON catalog is the `dump` text of its value inside them. Variable names ignore letter case and treat `_` and `-` as one character (vendor documentation): `$strRun_User$`, `$strrun-user$` and `$STRRUN_USER$` are one variable, and a store under any spelling writes the declared variable, an input included, overwriting what the caller passed. `profile` § VARIABLE SPELLINGS lists every variable written in several spellings. A key the dictionary does not hold is no error: `$name{key}$` retrieves a null value and `Dictionary.get` a blank one (vendor documentation) — a sub-bot's returned dictionary without that output reads empty. A list index starts at 0; what `$name[n]$` returns for an index past the list's end is not documented (an error, or an empty value — word both, a split on a separator whose part is missing being the usual case), while the Legacy Automation package's `$name.LegacyAutomation:getLegacyIndexValue(n)$` of migrated bots returns the list's first item for an index past its size (vendor documentation). `.String:toNumber` of a text that is not a number has no documented result, so it has two readings to word, with the one the rebuild follows flagged `*[Inferred]*`: an error, or 0 — the vendor documents positive, negative and decimal numbers and asks for commas to be removed first. `FILE` values are `file://<path>` or `repository:///Automation Anywhere/Bots/<path>`; `%20` and `%3B` are URL-encoded. CREDENTIAL values are references (`lockerName` / `name` / `attributeName`), never secrets; a reference with empty locker and name (the script prints `vault:/.`) is a **placeholder left in a disabled or unused command**, not an account. A literal is a Configuration Question default when its value is open, otherwise a fact stated where it acts (the skill's Configuration Questions rules). Never copy a literal assigned into a variable whose name contains `password`, `pwd`, `secret` or `token`: bots carry such literals (pitfall 9) and the inventory script redacts them. An empty literal is printed `""`: a value left empty, never a masked one.

**Encodings a reader of `dump` output (or of the raw JSON) must know** — the script handles all of them; the guide states them so a Source Map row and a business rule are read from the right channel:

- **Outputs are node-level, not attributes.** A command's result goes to the node's `returnTo`: `type: VARIABLE` (`variableName`), `DICTIONARY` (a map of callee output → caller variable on `runTask` and `Database.store`), or `SESSION` (a session opener). A `catch` carries a node-level `returns` map (`errorMessage`, `errorLineNumber` → variables). A loop iterator's own `returnTo` names the loop variable, or, on a table-row loop, maps each column to a variable that may be named otherwise (`{Path: $vFolder$, Days: $vDaysToKeep$}`). Nothing about a command's outputs is in `attributes[]`.
- **Every value carries every channel.** A value object holds `string`, `number`, `boolean`, `expression` and more side by side, the unused ones empty; the one that counts is the one its `type` names — a NUMBER's literal is in `number` while `string` is present and empty. Read `expression` first, then the channel the type selects; a reader that picks the first channel present reads every number as an empty string.
- **Booleans arrive in three encodings, the text form the usual one.** A BOOLEAN whose `boolean` channel is the **text** `"true"` / `"false"`; a BOOLEAN whose `boolean` is a JSON boolean; a STRING whose `string` is `"true"` / `"false"` (`String.*` flags such as `isCaseSensitive`, `isRegularExpression`). A BOOLEAN may carry an `expression` (a variable) instead. Compare the text, never its truthiness: `"false"` is a non-empty string, and a truthiness test turns every case-insensitive condition into a case-sensitive one and every `continueOnError: "false"` into a continue. An empty `boolean` channel is unset, not "false".
- **A condition chain's join sits on each link.** A chain is one `condition` attribute whose further conditions nest under `operatorAttribute`: each link is `{operator: AND | OR, value: <the next condition's kind>, attributes: [its operands], operatorAttribute: <the link after it>}`, and a parenthesised group is a `groupAttribute`. An attribute *named* `operator` inside a condition is its comparison (`EQ`, `INCLUDE`), not a join. Bots converted from Enterprise 11 also carry an `operator` attribute (`AND` / `OR`) on the node beside the chained condition, repeating the join its links carry; a node-level `operator` that differs from a link's is a finding to report, not to resolve. A reader that keeps only a condition's `name`, `value` and `attributes` loses every link after the first, and reports an AND / OR as missing when the file holds it.
- **Settings nest.** An option can sit in an attribute's own `attributes[]` rather than beside it: a `times` loop's count under `iterator` (`iterator.attributes[name=times]`, a NUMBER literal or an expression), a query export's file path under `doExport`. Look a setting up by name through one nesting level before concluding it is absent.
- **Tokens nest and abut.** `$table[$row$]{Column}$` puts a token inside a subscript and a column in braces; `$a$$b$` is two adjacent tokens (the common way a native bot builds a path tail — `<prefix>|$base$$counter$`). A flat left-to-right `$…$` scan mis-tokenises both; the variables a step reads are found by bracket depth. A `$$` outside a token is one literal dollar: an OLEDB range `[$sheet$$$$cell$:$cell$]` is `<sheet>$<cell>:<cell>`, and `$$name$$` in a message is the text `$name$`, not the variable's value.
- **`$<Package>:<Value>$` with no variable of that name is a value a package computes**: the source platform's own (`$String:Tab$`, `$String:Enter$`, `$String:Newline$` — the literal they name; `$Clipboard:Clipboard$` — the clipboard text) or a customer-built package whose code is not in the export — that value is a Configuration Question or an input of the step, flagged, never an empty default. `$System:` names seen: `AATaskName`, `AATaskExecutor`, `AAControlRoom`, `Machine`, `Date`, `Year`, `Month`, `Day`, `Hour`, `Minute`, `Second`.
- **Timing units ride on the node and differ per command**: recorder `wait` and window `waitTimeout` are seconds; recorder `delay` and keystroke `delay` are milliseconds between keys; `Delay.delay` carries its own `timeUnit` (SECONDS and MILLISECONDS both occur). Word every wait in the unit its node states.
- **String command semantics as stored**: `String.replace` `startIndex` is 1-based (`1` = from the start) and `count = -1` means every occurrence; `isRegularExpression` decides whether `find` is a literal or a pattern; `String.subString` `startIndex` / `subStringLength` cut the value (a length is a truncation the business rule inherits — a name cut to the length of the field it is typed into); `String.beforeAfter` (the Extract text action) `getCharacters` names where the delimiter stands relative to the extracted text: `BEFORE` with `beforeString` X returns the text **after** X, `AFTER` with `afterString` X the text **before** X, each at its occurrence number (vendor documentation). `BEFOREAFTER` returns the text between `beforeStringInBeforeAfter` (the delimiter before the result) and `afterStringInBeforeAfter` (the delimiter after it), the second occurrence counted from the first delimiter's, extracted when either delimiter is found for `beforeAfterCondition` `OR` and only when both are for `AND` (vendor documentation; what `OR` returns when one delimiter is missing or empty is not documented — word it from the uses, flagged `*[Inferred]*`). `ifNoMatchFound` is part of the rule — `SOURCE` returns the whole text, `EMPTY` an empty one — and so are `trimSpaces` and `removeEnter`. The bots' own uses show the same reading: a folder name taken with `AFTER ".xlsx"` from `<name>.xlsx`, a key taken with `AFTER <TAB>` from the first column of a copied result list, a last name taken with reverse → `AFTER " "` → reverse, a `key=value` pair split with `AFTER "="` for the placeholder and `BEFORE "="` for the text that replaces it, a `<LEVEL> -> <text>` log message split with `AFTER "->"` for the level. A parsing rule is worded from these ("the text before the first TAB", "the text between the first `-` and the first `:`"), never from the command name.

## Target Resolution

1. **Window variable → application.** Every UI command names a WINDOW variable; its `window.path` executable and `window.class` give the application (`jp2launcher.exe` + `SunAwtFrame` = Java Web Start application, `javaw.exe` + `#32770` = a Java runtime dialog, `msedge.exe` + `Chrome_WidgetWin_1` = Microsoft Edge, `iexplore.exe` + `IEFrame` = Internet Explorer, `OUTLOOK.EXE` + `rctrl_renwnd32` = Outlook desktop, `Explorer.EXE` + `CabinetWClass` = a File Explorer window, `CredentialUIBroker.exe` = the Windows credential prompt). The `window.name` is the title with `*` wildcards; the business application's name is the title's stable word (`<App>*`). A window variable with empty `path` and `class` was never captured against a live window — title only. **The descriptor is a snapshot until a `Window.SetTitle` or `Window.assign` rewrites the variable**: from that line on, the commands that name the variable match the assigned title, and the descriptor in `variables[]` describes the window the bot had before. Read the assigned expression as the window's identity for the rest of the bot; a descriptor carrying `nameCaseInsensitive: true` matched its title without regard to case — a source fact to carry, whether or not the target's matcher has a counterpart. A title can be a regular expression instead of a wildcard title, a String or a Pattern condition with its own case option (vendor documentation; `dump` renders `win(pattern"…" regexFlags=…)`): the pattern is the window's identity. A window picked through the Browser option carries its kind and the tab's URL at capture (`windowType=BROWSER_IE tabUrl="…"` an Internet Explorer tab, `BROWSER_CHROME` a Chrome tab); whether the match uses the URL is not documented. A command whose window carries `resize(width=…, height=…)` resizes that window to the size it was recorded at before it acts (the Resize window option, vendor documentation) — the step's window handling, carried with the step.
2. **URL variables** (`<APP>_DEV_URL` / `<APP>_QA_URL` / `<APP>_PROD_URL`, `openbrowser.url`) → Configuration Question "Which environment URL?" with the host as default; the values live in the configuration workbook, not the export, so the default is the variable's role unless a literal is present (a frame `src` in a capture — `http://<host>/<launch page>.html` — gives the host).
3. **Mail server.** `emailConnect serverType=EWS` with `exchangeService`, OAuth `clientIdInteractive` / `tenantIdInteractive` = Exchange Online (Microsoft 365) through EWS; `EMAIL_SERVER` + `protocol IMAP` + `serverHost` = the named IMAP host; a browser login to `outlook.office365.com` / `login.microsoftonline.com` / a corporate identity provider page is the same mailbox reached through Outlook on the web to prime the OAuth token → Target Application "Exchange Online mailbox" plus a Configuration Question on the authentication method. A browser window titled `*Authentication Complete*` (the `redirectURL` of the EWS block, typically `http://localhost:<port>`) that a bot waits for and closes after every send is the OAuth redirect landing page — part of that priming, never an application. The question must say how an unattended robot obtains the token: the rebuild's mail connection in an interactive-token mode depends on an acquired token exactly as the source's `authType="Interactive"` connection depended on the browser priming, so a working intake needs either that mode with a token the robot can reach or another mode the tenant allows — a deployment decision, not a build one. The source runs the priming bot (kill the browser, open Outlook on the web, sign in through the identity provider) before **every** connect and every send; that repetition is the source's workaround, not a rule — the rebuild signs in once per run, before the first mail call, and every later call reuses the token. EWS is the protocol the source spoke to Exchange Online, not a requirement of the business: Microsoft is retiring EWS for Exchange Online in favour of Microsoft Graph, so the Microsoft 365 (Graph) mail connection, with an application registration granted the Graph mail permissions, is the alternative the Configuration Question names beside the faithful EWS connection.
4. **OLEDB connection strings** → Excel workbooks (Target Application "Excel workbooks (via OLEDB)"); `Data Source=` names the file variable.
5. **`runApp` / `taskkill` executables** are the applications above; `taskkill` never creates a Target Application row on its own.
6. **Shared folders** (UNC paths in literals: `\\server\share\…`) → Platform Dependencies (a storage bucket or the kept network share), never a Target Application.
7. Global values are assets (§ Platform Resources): `$@AAE_EmailSettings_*$` hold the Control Room's email settings; `$@AA_LocalMachinePath$` (with a `#UserName#` placeholder), `$@AAE_SQLConnectionString$` (a template with a `##DATABASE##` placeholder, a Secret asset when it holds a password), `$@CleanUpTaskConfigFilePath$`, `$@AAE_EnvironmentType$` are deployment settings. `$@AABasePath$` is the runner's local repository root (migration path resolution) and disappears in UiPath.
8. **REST URIs** live in configuration variables (a token endpoint, an input endpoint, an acknowledgement endpoint with a `{messageId}` placeholder); the literal test URLs in disabled commands give the host of the test environment → Target Application "<vendor> API" named after the host and path, its client credentials per environment as § Platform Resources states.
9. **`Chrome_WidgetWin_1` + `*.pdf*` title** = an Edge tab showing a PDF (the application's report viewer); the UI Automation read of its `Address and search bar` is "the URL of the PDF" → a browser Get URL, then a download.
10. **A C# DLL** (`DLL.Open` path from configuration) is not an application: it is code of the process, built as § Component Detection decides — a Build With rationale names a coded step only for a function no activity performs.

## Call Graph Rules

1. Edge = enabled `TaskBot.runTask` whose `taskbotFile` resolves to a bot in the export. Order edges by editor line. A disabled `runTask` is a dead call (Source Map); an unresolved path is an external or deleted bot (Source Map, "unresolved").
2. Roots = bots never referenced by an enabled edge. Leaves = bots with no outgoing enabled edge. One root is the process entry; several roots in one folder are several processes or one process plus superseded copies — decide by the folder's other bots and the migration journal, flag `*[Inferred]*`.
3. Depth-first from the root; siblings in editor order; a `runTask` inside a loop or a condition inherits that step's rule ("for each pending record, invoke …", "when login fails, invoke …").
4. **The same sub-bot called from many places is one step of the callee's component and a reference in each caller's step**: a notification bot called eighteen times is one "Send notification" workflow; the callers' steps say which notification they send. Never one workflow step per call site.
5. Argument bindings: `taskbotInput` keys are the callee's `input` variables; a key bound to the same-named caller variable is state pass-through, a key bound to a literal or another variable is a real parameter (`vProcessName="InvoiceMailIntake"`, `strCompanyCode="$vCompanyCode$"`). `taskbotOutput` and the node's `returnTo` map (`{ExceptionReason: $ExceptionReason$, …}`) are the outputs the caller reads. The Interface of a library component lists the parameters the callers actually bind, not every flagged variable.
6. Recursion is impossible (a bot cannot run itself); a `times` loop around a `runTask` is a retry (Error Handling), not a call-graph cycle.
7. MetaBot logic bots call each other (`ErpLogin` → `GetWindowTitle`, `GetErrorPopupText`); these are edges inside the library component and become invoked workflows of the same library.
8. **Logger bots are not edges of the workflow.** `profile` lists them; `cards` counts their calls separately and `dump --compact` renders each call as a log line. A component's step count never includes them.
9. **A sub-bot that ends itself** (`TaskBot.stopTask` after setting the error variables) returns to the caller like a normal return; the caller's `if $vErrorStatus$` decides. Word the sub-bot's stop as "the step ends with {error}" inside the caller's step, never as a process stop.
10. **Variants of one bot** (`_V1` / `_V2`, a regional copy) are one workflow: diff them (`dump --compact` of both) and record the difference — a logout timer and relaunch added in V2, a different credential and mailbox URL in the regional copy — as an argument or a Configuration Question, and the older copy as a Source Map row of the same step (called only by the session check).
11. **A result-set loop that assigns every row to the same variables** keeps the last row (a controller bot reading "the detail row to process"); word it as "take the row the procedure returns" and flag the last-row behaviour.
12. **Result-set loops nested on one session.** An inner `iterators.resultset` loop over the session an outer one iterates, with or without a query of its own run first: each nested loop's dataset follows the query being executed (vendor documentation), and what the outer loop iterates once the inner query ran — its own rows, or the inner query's — is not documented. Word both readings where they differ and flag the one the rebuild follows `*[Inferred]*`.

## Expression Translation

Conditions are structured, not expressions: `{variable} {operator} {value}` with `EqualsTo` / `EQ` = "is", `DoesNotEqualTo` / `NEQ` = "is not", `INCLUDE` = "contains", `NOTINCLUDE` = "does not contain", `GreaterThan` / `GT` / `GreaterThanOrEqualTo` / `GTE` / `LT` / `LTE` = "exceeds" / "is at least" / "is less than" / "is at most"; a string test carries its case rule — `matchCase: true` = "exactly", `false` = "in any case" (§ Signals, `If` row). Several conditions on one `If` are joined by its `operator` (AND / OR); a native bot nests them as groups (`groupAttribute` / `operatorAttribute`) which `dump` renders with parentheses — keep the parentheses in the wording ("(contains `error` and not `Question`) or contains `<error code>`"). A chain that mixes AND and OR **without** a parenthesised group has no documented precedence in the source platform (the vendor documents And and Or for two conditions and a group for anything more): `dump` renders it left to right and marks it `[mixed AND/OR, precedence unstated]` — word the reading the surrounding branches make plausible and flag it `*[Inferred]*`, never silently pick one. A `WHILE` loop's condition reads "until {condition is false}"; `dateVariable` compares a date field to a fixed date ("on or after 11 June 2024"); `fileDate … Days=5` reads "modified within the last 5 days"; `tableRowCondition GT 0` reads "when the table has rows". Arithmetic hides in `Number.assignToNumber input="<base>+$row$"` (a row offset) and in a minute difference (`$end$-$start$`, a timeout). Variable transforms in values (`$x.String:toNumber$`) carry no business meaning; `$Loop-Files-1{extension}$ EqualsTo "xlsx"` reads "the file is an Excel workbook". String flags stored as text (`"TRUE"` / `"FALSE"` in STRING variables) are booleans. Translate with the table in the skill's Business Rules wording. The SQL in `sqlQuery` / `insertUpdateDelete` is a business filter or a write-back: translate `WHERE [Status] IN ('Received','Validated')` as "whose status is Received or Validated"; keep column names as field names in the genome (they are the data schema, not code).

## UI Target Locators

Every `Recorder.capture` (and every capture used as a condition) carries its recognition data inline — there is no object repository in an export. `targets` decodes it into one normalized record per capture (`a360-targets.json`): `technology` (`JAVA`, `HTML`, `MS_ACTIVE_ACCESSIBILITY`, `MS_UI_AUTOMATION`, `SAP`, `AISENSE`), `controlType` (`TEXTBOX`, `PASSWORD_TEXT`, `BUTTON`, `LABEL`, `CLIENT`), `criteria` (only the properties the author **enabled** for matching, `name → value`, values may be variable expressions), `object` (the decoded blob: accessible `name`, numeric `role`, `description`, `className`, `id`, the accessibility `path` of child indexes, bounds, the recorder's `attributes` list; an AISense capture has no object tree and carries `vision` instead — the control a vision model recognised and its anchors, [selectors-guide.md § AISense](selectors-guide.md)), `window` (the resolved WINDOW variable: title, class, executable), `action`, `value` (redacted for password fields), `credential`, `screenshots` (the PNG names under `<Bot>Metadata/`), `line`, `disabled`, and `settings` — every other attribute of the command by name (its wait, advanced wait, key delay, background flag): the catalog keeps a command's settings by denylist, never by a list of names worth keeping, which drops the ones nobody listed. Keystroke commands (keys, the delay between keys, every setting) and window operations — mouse clicks at a point included — (every setting) are listed per bot with their window; a window records its title, class, executable, whether its title was matched without regard to case, its title pattern, its kind and tab URL when picked as a browser tab, and the size a command resizes it to. **A second identity channel** is listed per bot as `scriptedTargets`: a string literal or expression anywhere in a node — a sub-bot call's input binding, the argument of a script, DLL or package call, a variable default, an id embedded in a script statement — that is itself a UI identity of a scripting model (a SAP GUI scripting id `wnd[n]/…`, a selector fragment). A bot that drives an application through a scripting wrapper library carries every one of its targets there and next to none in `controls` (dozens of distinct ids against a handful of captures); the wrapper's own semantics are the customer's, the identities are the application's ([selectors-guide.md § SAP GUI](selectors-guide.md)). The Source Map's inventory counts both channels. Formats and per-property translation: [selectors-guide.md](selectors-guide.md). Extraction records only counts (captures per technology and control type, how many disabled, how many located by position only) in the Source Map; execution derives the catalog at migration preflight and turns it into Object Repository targets (the skill's migration at execution).

Several captures usually target the **same control** (the recorder attached a fresh capture each time the author recaptured after a run-time error — the disabled twin sits one line above the live one): collapse by window + criteria + object name at execution (the skill's Object Repository identity rules). A control whose only enabled criteria are `Path` / `Index` ran positionally: its disabled `Name`, when the capture holds one, identifies it ([selectors-guide.md § Format-wide conventions](selectors-guide.md)), and without one it stays positional (low confidence, live capture owed); one whose `Index` is a variable is a row of a grid (§ Composite actions).

`a360-process-data.json` is the process inventory `check-genome.mjs` reads (`[{id, name, recordset: null, loggerBot, calls: [{calleeId, recordset: null}]}]` plus path, folder, inputs, outputs, screenshot and log counts, argument bindings — a call's `outputs` are its output map and the node's own `returnTo` map (callee output → caller variable), and `outputsTo` the one dictionary variable that receives every output); `a360-data-sources.json` is its recordset list (`[{id, name, kind, usedBy}]`, kinds `config-file`, `workbook`, `database-connection`, `query`, `stored-procedure`, `api-endpoint`, `dll-file`, `dll-function`, `csv-file`, `text-file`, `pdf-file`, `download`, `json-file`, `xml-file`, `xml-node`, `script`, `credential`, `mailbox`, `mailbox-folder`, `mailbox-send`, `folder`, `file-operation`, `log-file`, `screenshot-file`). Commands inside a disabled subtree are not sources: the script propagates a node's `disabled` flag to its whole subtree before counting. A source is one thing the bots use (a mail account, a workbook, a procedure); each use is cited by bot name, id and line (`usedBy`), and a use whose details differ from the entry's own — a second mail through the same account with its own subject and attachments, another sheet of the same workbook — keeps them under `perUse`. A source is named by the text that identifies it — a path, a URL, a connection, a procedure, an account — and its id is derived from `kind|<text>` the same way as bot ids. A query is one command at one line: its id is derived from the bot's repository path and the line, and its name is `<VERB> <tables> at <BotName> (<bot id>):<line>` — its verb and the tables it names (a worksheet without its `$`), or the variable that holds it in their place — because its SQL spans lines, can hold `|` and backticks and repeats across bots, and copied bots share their name and their lines. The SQL is the entry's `query`. A name is what a step table's Data sets cell cites, `` `Name` (id) ``, so it holds no `|`, backtick or line break: a text that does is named with each run of spaces and line breaks folded to one space, `|` written `¦` and a backtick `'`, and kept whole under `text`. Rules: the runner-number branches (runner 1 / 2 / 3) are one data dimension (account per runner), never three steps; a `readStatus` that differs between the branches (`UNREAD` in two, `ALL` in the third) is a source quirk to carry over and flag, not to correct silently; template placeholders `{0}`, `{1}`, `{2}`, `{3}` and the order they are filled in are the notification's data contract.

## Provenance the Source Map must carry, and the inventory shape

Export identity: the export root path, the Control Room repository root the paths start with (`Automation Anywhere/Bots`), the bot count, the package versions that date the export (`profile` § PACKAGES), whether bots carry migration journal ids (Enterprise 11 origin) or native `Created Date` headers, whether a `manifest.json` is present (its file count by content type and whether its scanned dependencies match the bots' enabled edges — `profile` § MANIFEST), and the files present beside the bots (configuration files, templates, scripts, assemblies — `profile` § FILES). Source object identity: `` `BotName` (id) `` with the id from `profile` / `cards` / `data` (CRC-32 of the repository path), because bot names repeat across folders and a moved copy keeps its path — the same id is what `dump` takes. Per workflow step, its step table row: Source objects the bots the step was built from, `` `BotName` (id) ``, or `` `BotName` (id, lines <FROM>–<TO>) `` with the editor line range (`dump` line numbers) when one bot yields several steps; Data sets the `a360-data-sources.json` entries those bots read, `` `Name` (id) ``; Captures the number of enabled `Screen` package nodes inside the step's lines (screenshots, § Evidence); a recorder capture is a UI action on a control, not a screenshot (§ Evidence for its metadata PNGs); a library workflow's callers in Notes. A node is cited by bot id + line, never by its `uid`: uids are unique inside one bot only, and copied bots share them (§ Inventory and Exclusions). Checkpoints (for test components only; a process export has none unless the bots assert). Inventory counts: bots, lines (enabled / disabled), window variables, recorder captures (enabled / disabled, per technology), keystroke commands, credential references, data sources, dead calls, unresolved callees.

## Evidence

Bots log to a text file on almost every step — through `LogToFile.logToFile` in a migrated export (a large share of all lines), in a native one often through a logger bot or a customer logging package, with `LogToFile` writing data files (§ Signals) — and take a screenshot in catch blocks and on business errors: each `Screen` package action — Capture desktop, Capture area, Capture window (`captureDesktop`, `captureArea`, `captureWindow`) — saves one to an image file (vendor documentation), a desktop one named `<Screen>Error_<timestamp>.png` under the process's `Screenshots` folder. That is the skill's blanket evidence policy: `profile` § EVIDENCE AND NOISE and `cards` report log and screenshot counts per bot — state the policy once per component (log lines become log messages at the same points, in the source's wording and level — the skill's table of source steps that are not UI actions; a screenshot per handled error becomes screenshot-on-failure attached to the job), never a workflow step per log line. After a scripting-wrapper verb, a line narrates the action and the status the verb returned (`Press <button>. | Status: $<result>$`); the rebuild logs the narration without the status, which has no counterpart once the activity raises on failure. Where the house template's execution-log mail attaches the log file (pitfall 28), a step of the export reads it, so the file is data the rebuild keeps writing; otherwise the job's log in Orchestrator replaces it by default (the skill's evidence policy). `MessageBox` commands are the author's debugging (almost all disabled in a migrated export — but often **enabled** in a native one, echoing configuration, credentials and intermediate values); an enabled `MessageBox` that does not close itself blocks an unattended run (§ Step vocabulary) and is an Error Handling finding (state the count once, in Error Handling § Global), not evidence. A **logger bot** (inputs: message, level, file path, name, extension, task name; a level filter `ALL` / `TRACE` / `DEBUG` / `INFO` / `ERROR` / `NONE`; one CSV line `datetime,level,task,message` per call; the message convention `<LEVEL> -> <text>`) is the native equivalent of the migrated bots' direct log lines: `profile` and `cards` count its calls per bot; the genome states the level names and the line format once as the evidence policy and the rebuild maps them to the robot's log levels. Native bots also keep a second, dated per-bot text log under the runner's Documents with `At <line>;<variables>` lines — the author's trace, useful for wording, never a step. Metadata PNGs are the recorder's captures of each control at design time: useful to an executor deriving a target (the screenshot shows the widget), never a run-time artifact.

**Checkpoints for the Source Map.** A process export asserts nothing formally; the checks it does make are business decisions (a popup text read and compared, a count queried) and belong to Business Rules. When a bot is a test (it only reads and compares), its GETPROPERTY-and-compare pairs are the checkpoints: record them as `line — asserts — expected — screenshot taken?`. A check whose result the bot only logs (a wrapper verb's returned flag written to a log line) or whose failure its `catch` swallows is not a checkpoint; a check inside a loop asserts on every pass, one on a branch only there (the skill's rule that every source checkpoint has a parity row).

## Framework Pitfalls

1. **Disabled code is everywhere and looks like logic.** A large share of the lines in a migrated export is disabled: whole `Step` blocks of the pre-migration Internet Explorer flow, the recapture twins of controls, the v11 credential comments, the IMAP connection commands replaced by OAuth. Read `dump --compact` (disabled subtrees folded) for the behaviour and the full dump only to understand history; put the superseded flow in the Source Map as dead code.
2. **Bot Migration plumbing is not behaviour.** Variables `m-string-start-in-path*` (a path staged for the next command), `M-Logic-Return-Dict-*` (a MetaBot's returned variables as a dictionary), `M-IsBotExecutedSuccessfully` and `M-Error-Description-Default-Val` (the `finally` / `throw` idiom marking the run Failed; the default value is empty), `Loop-Counter-*` (the name only: its value is the pass number, and a test on it is the loop's limit — § Signals — Bot, the `WHILE` row), `Loop-Dataset-Column*`, `Loop-Files-*`, `Loop-Email-Response-*`, `Prompt-Assignment` (`Test-Value`), `my-list-variable`, the `.LegacyAutomation:parseVariableOperation` re-assignment after every assignment, `.LegacyAutomation:getAbsolutePath($@AABasePath$)` around every path. `profile` § MIGRATION PLUMBING counts them per bot. None of it enters the genome.
3. **Every variable is flagged input and output.** Migrated task bots declare 50–90 in/out variables and pass them all on every `runTask`; the real interface is the handful the callee reads or writes. Derive it from the body and from the bindings that carry a literal or a differently named variable.
4. **Empty error text means success.** Sub-bots return an error reason built from `Error-Description`, whose migration default is empty; a caller that tests the returned text for a word (`INCLUDE "Completed"`) can never see it and takes the failure branch. Carry the caller's rule as written, flag it `*[Inferred]*` as a suspected defect, and word the intended behaviour ("an empty error reason means the update succeeded").
5. **N identical branches per runner.** A runner-number switch repeats a long block per bot runner, differing only in the credential and in accidental drift (one branch reads all mail instead of unread mail, one parses the company code with an extra step, one moves mail without filtering by subject and sender). Extract one step with the account as a parameter and list the drift as source quirks.
6. **`taskkill` is cleanup, not an application.** Migrated bots force-close Java, Edge, Excel and Outlook before and after work; word it once under Error Handling / cleanup.
7. **Positional Java locators.** Java controls are matched by accessibility `Path` (`1|1|2|1|1|1|1|1|1|3|1|1|1|1|1|5`) and `Index`; the same control appears with `-1|…` and `1|…` paths in its recaptured twins and identical `Name`s repeat per grid row. `Name` + `Role` are the reusable identity; `Path` / `Index` are position ([selectors-guide.md § Java](selectors-guide.md)).
8. **Window variables are snapshots.** A WINDOW variable records the handle, size and the Java runtime's executable path of the capture session (`jre1.8.0_281`, `jre7`, `jre1.8.0_331` across bots); only the title (wildcard or regular expression), class and executable *name* carry over. Titles differ by browser generation (`<App>*` for the applet frame, `<App>*- Microsoft Edge` for the launch tab, a different title for the login frame).
9. **Plaintext secrets.** A literal typed into a password field or assigned into a password-named variable (`str<App>Password`) is a secret in the export. The inventory script redacts the value wherever it appears; the genome names the credential asset and the report says the export contains a plaintext password without repeating it. Test recipient addresses and a runner's personal user name in disabled test commands are personal data — configuration values, not defaults to keep.
10. **Sheet names read through a formula.** `SetCell` `=MID(CELL("filename",A2),…)` into a spare cell followed by `GetSingleCell` is the v11 idiom for "read the active sheet's name"; it also **writes into the input file** (a spare cell). Word the intent (find the sheet whose name contains the fragment) and note the side effect.
11. **Excel through OLEDB.** `Database.*` commands with an ACE OLEDB connection string are workbook reads and writes; `[Sheet$]` is a sheet, the SQL is the filter or the write-back. `dosaveData` on `disconnect` is meaningless for a workbook. The HDR and IMEX flags in the connection string are part of the read rule (whether the first row holds the headers, whether mixed-type columns are read as text) and are stated with the step (`CONNECTIONSTRING` itself is a config value with a `FileName` placeholder). With `IMEX=1` the driver guesses each column's type from its first rows (eight, the driver's default): a column whose sampled rows mix text with numbers or dates — a header row read with `HDR=No` makes it so — returns every cell as the text the sheet displays, number format included (a date as the cell formats it, an amount with its thousands separator and currency text); a column of numbers or dates only returns typed values, and a text cell below the sampled rows of such a column comes back empty.
12. **`continueOnError` plus a string flag.** Callers run sub-bots with `continueOnError: true` and then test a `blnIsTaskError` string (`"TRUE"`) the sub-bot set, calling a shared exception logger and `stopTask`. That is the process's exception routing: one Error Handling § Global entry, not a rule per call site. The flag is stored as the text `"true"` / `"false"` (§ Value syntax): read its value per call — most calls in a native export carry `"false"`, and those callers do not continue, the sub-bot's error ends the caller.
13. **Comments drift.** Section comments (`START: Email processing.`, `END: Download Attachment File`) are copy-pasted around unrelated calls; log messages are the reliable narration. Bot descriptions and `Step` titles drift the same way in native exports — a description pasted into twenty bots, a phase title heading a block of constants — so a description is verified against the steps before it words anything (§ Detection). A MetaBot logic's description ("Metabot logic to …") tends to hold because the logic does one thing; verify it all the same.
14. **The launch page and the application are different windows and technologies.** A browser tab (HTML: click the launch button inside a frame) starts a Java Web Start applet (JAVA: everything after); Java's own dialogs (`Security Warning`, `Java Update Needed`) are Win32 (MSAA) windows of `javaw.exe` / `jp2launcher.exe`; Edge's toolbar is UI Automation. One business step (open the application) spans four technologies and three windows — the Target Applications table names the application once, the selectors guide maps each technology.
15. **Native bots pass 40–100 variables on every call.** A controller declares every setting as in / out and binds all of them by name on each `runTask` (`in{+55 pass-through}` in the compact dump). The real interface is the handful of bindings that carry a literal or a differently named variable (`cards` lists them as "real parameters passed"); the same-named ones are shared state. Never write a library Interface from the flags.
16. **`Database.store` is a stored procedure, not a "store".** The `query` attribute holds the procedure name, the session names are usually the procedure names too (`susp_Getting_…`), and one procedure call replaces what a migrated bot did with a dozen workbook commands. The result set drives the next loop; output parameters (`InputOutput`) come back through the node's `returnTo` map. Read the procedure's parameter names as the data contract; the procedure body is not in the export.
17. **The database is the work list and the run controller.** Master / detail tables, a per-runner hand-out procedure, a master-validation procedure returning `<flag>#<instruction>`, login tracking, notification trackers, templates. Word the protocol values (`Success`, `stop`, `delete`, `apierror`, `Stop`) and their effects; do not invent a queue: the work tables are the As-is item store, and a queue is a split option (the skill's Transactional Shape). Recurring shapes of that controller, each one rule or one Error Handling entry, never a step per call site: **runner election** — every runner runs the same root, one procedure answers `<send flag>#<instruction>` and the runner with the flag does intake and reporting while all runners process; **reset for reprocess** — a procedure resets half-done items at start and on an unhandled error, never in between; **deferred notifications** — a non-master runner inserts the mail into a tracker table and the master replays the trackers; **login tracking** — a procedure returns `Stop` when the last login is too old, the bot force-closes the application, logs in again and records the login; **post-item reconciliation** — a raw query corrects the item's status from the presence of its output rows (`Completed` without output → `Error`; `Error` with output → `Completed`); **configuration re-read mid-run** — the root re-reads the configuration procedure on a day change, and a library bot may call the process's configuration bot (a layering inversion: rewrite it as arguments the consumer passes).
18. **Secrets hide in disabled test commands and in configuration rows.** A disabled `restGet` carried a literal bearer token (a JWT) in its `Authorization` header and a disabled `restPost` a literal client id and secret; the database configuration carries `<App>UserName` / `<App>Password` rows that the bots read and echo in a message box while the vault credential is what they type. The inventory script redacts JWTs, bearer / basic literals and every value of a `passw` / `pwd` / `secret` / `token` / `api key` attribute wherever they appear; the genome names the credential assets, reports that the export contains such literals, and never repeats them. A functional mailbox address is a configuration value, not a secret.
19. **Copies of a MetaBot inside the process folder.** Native exports of a tenant with MetaBot-era libraries carry the generic application bots as task bots beside the process (enter credentials, change a context value, press a toolbar button, wait for a screen, common screen navigation `_V1` / `_V2`); disabled `runTask` commands still pointing at `My MetaBots/…` reveal the origin. They are the UI library (§ Component Detection), and the same bots appear in the sibling process's export under the MetaBot folder — one library serves both genomes.
20. **Bot variants.** `_V1` / `_V2` pairs (the session check still calls V1, the process calls V2), a regional copy of the mailbox sign-in differing only in the credential and the mailbox URL, a `_SingleBot` copy of the notification bot without the template step, and **two differently named handlers of one dialog** (a native popup handler and an older one, both live, with different decision tables) — diff them; one workflow with an argument, the union of the decision tables as its rules, the older copy a Source Map row.
21. **Status strings drift.** Error flags are `STRING`s holding `TRUE` / `FALSE` — and `FASLE` on reset lines, `""` after a reset, `Fail` from one library bot, `true` in lower case from another; callers test `NEQ "TRUE"`, `INCLUDE "FALSE"`, `EQ "FALSE"`, `NOTINCLUDE "TRUE"` interchangeably. Translate every test to "when the step reported an error" and list the spellings once as a source quirk; a catch that sets the flag to `FALSE` (a write-back step) hides its own failure — flag it.
22. **Enabled message boxes in production bots.** Native bots keep debugging message boxes enabled (configuration echoes, `Step 1 :` dumps, popup echoes). Each one that does not close itself blocks an unattended run, and each one that does holds it for its seconds (§ Step vocabulary); count both kinds in the Source Map inventory (`profile` and `cards` print them as `<waiting>+<closing> on`) and state the finding once in Error Handling § Global.
23. **Positional Java locators dominate native captures.** A large share of the enabled controls in a native export is located by `Path` (plus `Top`, the y-coordinate) only; grid cells and tree rows use a `Path` whose last segment is a counter; the same field is captured under two path variants (`…|2|1|1|198` / `…|1|1|1|198`) in a try / catch pair. `Name` + `Role` are the reusable identity; a toolbar dispatcher's buttons are all positional ([selectors-guide.md § Java](selectors-guide.md)).
24. **Environment detection through Control Room values.** `$@AAE_EnvironmentType$` / `$System:AAControlRoom$` compared to `dev` / `uat` select connection strings, URLs and the API credential (`_UAT` locker); a hardcoded server-address replacement in the connection string (`<old host>,<port>` → `<new host>,<port>`) is a migration left-over to report as a Configuration Question default.
25. **`taskkill excel.exe` before every OLEDB read**, a kill-sleeping-connections procedure before the work loop, and a **force-close every N cycles** (`if $counter$ > 102 → taskkill java.exe`, then re-login) are the source's workarounds for leaked handles and a degrading application; word them once under cleanup / Error Handling with the cycle count, never as steps.
26. **Regional variants send from another mailbox.** A regional notification is sent from a second functional mailbox with a second credential and a hard-coded copy recipient; the plain-text copy of every notification is sent from a sibling process's mailbox. Each account is its own credential asset (the skill's Platform Dependencies rules); the cross-process mailbox is a source quirk to report.
27. **A "dead branch" claim needs the whole condition.** Nested `if`s joined by `OR` are the migration's idiom for a case analysis (`if empty OR contains R OR contains F` → `if contains R OR contains F` → "Already Completed status."). The inner branch is reachable for every value the outer `OR` admits; only a value the outer condition excludes makes it dead. An extraction that reads the outer condition as "empty" calls such a branch dead, and the build that follows the genome drops the source's already-completed handling. Prove a dead branch from the condition text (the skill's call-graph rules) before the Source Map says so.
28. **A customer bot template is not steps.** Native exports built on a house template repeat the same blocks in every bot: an initialise section (configuration file → parameter table, folder structure, log start, mail authentication), a `try` around the logic, plus "Add your logic here" and "DO NOT USE Stop Task" comments. The template has two forms: the **master** bot's `catch` logs the error and line and its `finally` sends the execution-log mail, cleans up and rethrows when the run failed; a **sub-bot**'s `catch` logs and takes a screenshot, its `finally` only logs the end, and the error leaves as an output (an error-message variable) the master tests after the call. Read the library bots' own `catch` / `finally` too (a `throw` inside `finally`: § Signals — Bot, `ErrorHandler.try`). Read them once as Error Handling § Global and Deployment; the Source Map lists them as a `Framework files` row; a sub-bot's `loop for times(times=1)` around its whole body is the template's `break` wrapper, not an iteration. Every other `times` loop is read by its count — a count of 2 or 3 around a logon is a retry of the whole logon, a count equal to a column count is a pass over the row's cells.
29. **A positional configuration table with the file absent.** A template that reads a configuration file into a table and addresses settings by row (`$arrParams[34][0]$`) leaves the genome with row numbers and no values when the file is listed in the manifest but not contained (pitfall row in § Detection). Derive each row's meaning from every use (a path joined with a drive letter, a sheet name, a recipient list split on `;`, an end time compared as `HH:mm`), state it as a Configuration Question with the row number and no default, and never invent a value. The template may read the same file twice — into the row table and into a dictionary keyed by row number — and an override map (start arguments applied on top of the file) patches only one of the two views: state which settings an override can change, from the view each setting is read through.
30. **A scripting wrapper hides the UI behind DLL calls.** When a MetaBot library wraps a scripting assembly, the processes show `TaskBot.runTask` lines with the element id as a binding and almost no `Recorder.capture`; `profile` § UI CAPTURES then understates the UI surface by an order of magnitude. Read `targets` § scripted targets for the real inventory, and treat each wrapper call as the UI action it is (§ Signals) — in the genome a step of the calling component on the element the id names, never a call into a library of verbs (§ Component Detection). The recorder appears at a handful of points (a system-messages button during logon, a date field, a check box) — why the author left the wrapper there is not in the export; those captures show the technology and window of the application the wrapper drives. The wrapper's window checks (`windowExists` on a dialog's title) have no scripting id: they become a check on the modal screen named by that title.
31. **Copies of one bot in several process folders.** A logon bot kept under each process (the same lines, differing in a configured title and in wait timeouts) and a MetaBot logic duplicated as a shared task bot (differing in the assembly copy it loads) are one workflow each; the call graph resolves the copies by path and id, so both appear as callees, and every catalog names a bot by name **and** id — bots named alike are different nodes, and `dump` reads each copy by its id (by name it lists the copies instead of picking one). Merge them in the library and carry every difference as an argument (§ Component Detection); diff dumps that `check` passes.
32. **Two-tier configuration with an override.** A Control Room global value (with a `#UserName#` placeholder) names a deployment XML file, the file names the configuration procedure and the connection strings, the procedure's rows fill fifty-odd same-named variables, and one of them (the connection string) is then **overwritten** by another global value with a `##DATABASE##` placeholder and a host replacement. Word the chain once under Platform Resources (asset → file → procedure) and the override as a Configuration Question default; the fifty keys are Configuration Questions grouped by theme, every key named inside its question so execution can still map them.
33. **Guards on state nobody writes, and counters advanced twice.** A "ran recently" guard on a marker file no command creates can never fire; a walk loop that increments the same counter in two consecutive lines skips every other row. Carry the source's rule, flag the suspected defect `*[Inferred]*`, and word the evident intent (the marker is written at the end of a run; one increment per row) — the classes are "guard on a file no command creates" and "same counter incremented twice", worth a search in every native export.
34. **Business screenshots are evidence at decision points.** Native bots take named desktop screenshots at business decisions (`_QuoteRef.png`, `_ChargeCode.png`, `_MassInvoicePrint.png`), not only in catch blocks: state them once as the evidence policy (a screenshot per named checkpoint, attached to the job) and name the points in the Source Map so execution attaches evidence at the same places; they are not steps.
